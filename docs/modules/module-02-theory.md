## 1. Модель адресации

Три уровня, и каждый нужно держать раздельно в голове.

**Топик** — логическое имя. Физически не существует: это просто метка в метаданных, объединяющая набор партиций.

**Партиция** — единица физического хранения, репликации и параллелизма. Именно она является тем самым append-only логом из модуля 1. Живёт на диске конкретного брокера как каталог `<топик>-<номер>`.

**Оффсет** — порядковый номер записи внутри партиции. Монотонно возрастает, начинается с нуля, никогда не переиспользуется. Уникален только в пределах партиции: оффсет 42 в партиции 0 и оффсет 42 в партиции 3 — разные записи.

Полный адрес записи в Kafka — тройка `(топик, партиция, оффсет)`. Никакого другого способа адресовать запись не существует: ни по ключу, ни по содержимому, ни по идентификатору.

Из этого выводится то, что для многих оказывается неожиданностью:

**Порядок гарантирован только внутри партиции.** Если топик разбит на шесть партиций, у него шесть независимых порядков. «Глобального оффсета» топика нет и быть не может — он потребовал бы координации между брокерами при каждой записи, то есть ровно того, чего Kafka избегает.

**Оффсеты непрерывны, но не обязательно плотны.** После компакции или в транзакционном топике в последовательности появляются дыры: оффсет 5 есть, оффсет 6 удалён компактором, оффсет 7 есть. Потребитель это не замечает, он просто читает следующую существующую запись.

## 2. Ключ и выбор партиции

У записи есть необязательный ключ. Он определяет, в какую партицию попадёт запись.

### Ключ задан

```
partition = murmur2(keyBytes) & 0x7fffffff % numPartitions
```

Хеш от байтов ключа по модулю числа партиций. Три следствия:

**Одинаковый ключ всегда даёт одну и ту же партицию** — при неизменном числе партиций. Отсюда гарантия порядка для ключа.

**Распределение зависит от кардинальности ключа.** Ключ `country` в сервисе, где 80% трафика из одной страны, даёт перекошенные партиции: одна забита, остальные пустые. Это data skew, и лечится он только сменой ключа.

**Алгоритм зафиксирован в протоколе, а не в реализации.** Клиенты на Java, Go и Python выбирают одну и ту же партицию для одного ключа — иначе смешивать клиенты было бы невозможно.

### Ключ не задан

Здесь история менялась, и знать текущее состояние важно.

Исторически записи без ключа распределялись по кругу (round-robin). Это давало равномерность, но плохие батчи: подряд идущие записи расходились по разным партициям, каждый батч получался маленьким.

С KIP-480 появился sticky partitioner: продюсер выбирает одну партицию и льёт в неё, пока не заполнится батч, потом переключается на следующую. Батчи стали крупнее, пропускная способность выросла.

С KIP-794 (Kafka 3.3+) поведение по умолчанию изменилось снова. Если `partitioner.class` не задан, используется встроенный «строго равномерный» вариант, который учитывает, насколько быстро брокеры подтверждают записи, и реже шлёт на отстающие. Это важно: при `partitioner.class=null` вы получаете **не** старый round-robin.

### Смена числа партиций ломает отображение

`numPartitions` входит в формулу. Увеличили число партиций с 6 до 12 — ключ, который раньше шёл в партицию 2, теперь пойдёт, скажем, в партицию 8. Записи с этим ключом окажутся в двух разных партициях, и их взаимный порядок перестанет быть определён.

Kafka не перераспределяет существующие данные при увеличении партиций. Старые записи остаются там, где были.

Практический вывод: **число партиций для топика, где важен порядок по ключу, менять нельзя.** Если рост неизбежен, закладывайте запас сразу либо стройте схему, где порядок обеспечивается иначе.

Уменьшить число партиций нельзя вообще, ни при каких условиях. Причина не в лени разработчиков: пришлось бы решать, куда девать данные из удаляемых партиций, как сохранить их оффсеты (которые уже закоммичены потребителями) и как не нарушить порядок. Ни одного корректного ответа нет.

## 3. Что такое запись

Единица хранения в Kafka — не отдельное сообщение, а **батч записей** (record batch, формат v2). Это важно для понимания всего остального.

Структура батча, упрощённо:

```
RecordBatch
├── baseOffset            оффсет первой записи
├── batchLength
├── partitionLeaderEpoch  для защиты от рассинхронизации при смене лидера
├── magic = 2             версия формата
├── crc                   контрольная сумма
├── attributes            биты: сжатие, тип timestamp, транзакционность, control
├── lastOffsetDelta
├── firstTimestamp
├── maxTimestamp
├── producerId            для идемпотентности
├── producerEpoch
├── baseSequence
└── records[]
    ├── length
    ├── attributes
    ├── timestampDelta    относительно firstTimestamp батча
    ├── offsetDelta       относительно baseOffset батча
    ├── key
    ├── value
    └── headers[]
```

Что отсюда следует:

**Сжатие применяется к батчу целиком.** Поэтому коэффициент сжатия сильно зависит от размера батча и однородности данных: сотня похожих JSON-ов сжимается в разы лучше, чем один.

**Оффсеты и таймстемпы хранятся дельтами.** Экономия места, а заодно причина, по которой нельзя просто «вырезать» запись из середины батча.

**Идемпотентность живёт на уровне батча.** `producerId`, `producerEpoch`, `baseSequence` — это то, чем брокер отличает повторную отправку от новой. Детали в модуле 3.

**Headers** — произвольные пары ключ-значение, не участвующие в партиционировании. Штатное место для трассировки, версии схемы, счётчика ретраев.

### Два вида времени

Атрибут `message.timestamp.type` определяет, что попадёт в поле timestamp:

- `CreateTime` (по умолчанию) — время, проставленное продюсером;
- `LogAppendTime` — время, когда брокер записал батч.

Разница принципиальна для `.timeindex`, для retention и для оконных операций в Streams. При `CreateTime` брокер доверяет клиенту, и кривые часы на клиенте приведут к тому, что записи будут удалены раньше или позже, чем нужно, а сегменты будут закрываться не вовремя (см. раздел 4).

Ограничить разброс можно через `message.timestamp.before.max.ms` и `message.timestamp.after.max.ms` (KIP-937; старый `message.timestamp.difference.max.ms` устарел). В Kafka 4.0 по KIP-1030 `message.timestamp.after.max.ms` по умолчанию равен одному часу: записи с таймстемпом из будущего дальше этого отклоняются.

## 4. Сегменты: лог на диске

Партиция не один файл, а последовательность **сегментов**. Заглянем внутрь:

```
/var/lib/kafka/data/labs.orders.created.v1-0/
├── 00000000000000000000.log          сегмент, записи с оффсета 0
├── 00000000000000000000.index        разреженный индекс оффсет → позиция
├── 00000000000000000000.timeindex    разреженный индекс время → оффсет
├── 00000000000000104857.log          следующий сегмент
├── 00000000000000104857.index
├── 00000000000000104857.timeindex
├── 00000000000000104857.snapshot     состояние идемпотентных продюсеров
├── leader-epoch-checkpoint
└── partition.metadata
```

**Имя сегмента — это базовый оффсет**, дополненный нулями до 20 знаков. Файл `00000000000000104857.log` содержит записи начиная с оффсета 104857. Это позволяет найти нужный сегмент бинарным поиском по именам файлов, без чтения содержимого.

**Активный сегмент** — последний, тот, в который сейчас пишут. У него особый статус:

- он никогда не удаляется по retention;
- он никогда не компактится;
- его индексы предварительно выделены (`log.index.size.max.bytes`) и обрезаются при закрытии.

**Когда сегмент закрывается и открывается новый (roll):**

| Условие | Параметр | По умолчанию |
|---|---|---|
| размер достиг предела | `segment.bytes` | 1 ГБ |
| прошло время с момента создания | `segment.ms` | 7 дней |
| индекс переполнен | `segment.index.bytes` | 10 МБ |

**Все три проверки выполняются в момент записи, а не по таймеру.** Перед добавлением батча брокер решает, поместится ли он в активный сегмент. Партиция, в которую перестали писать, не закрывает активный сегмент никогда — сколько бы времени ни прошло.

**Проверка по времени сравнивает таймстемпы записей, а не часы брокера.** Берётся максимальный таймстемп первого батча сегмента и таймстемп нового батча; если разница больше `segment.ms`, сегмент закрывается. Так работает с версии 0.10.1. Следствие: при `CreateTime` момент ролла определяет продюсер, и клиент с отстающими часами задерживает закрытие сегментов, а вместе с ним retention и компакцию.

**Закрытие не удаляет и не переименовывает файл.** Старый `.log` остаётся на месте, рядом появляется новый файл с базовым оффсетом следующей записи.

**Ограничения версии.** В Kafka 4.x минимальный `segment.bytes` равен 1 МБ (KIP-1030), максимальный — около 2 ГБ, так как параметр целочисленный. Минимальный `segment.ms` по тому же KIP планируется поднять до одной минуты в Kafka 5.0: учебные значения вроде `segment.ms=10000` на 5.x перестанут приниматься.

Это ключевой момент для понимания retention, к которому мы придём в разделе 7: **Kafka оперирует сегментами, а не записями.**

## 5. Индексы

Два индекса на сегмент, оба разреженные.

### .index — оффсет в позицию

Отображает относительный оффсет (относительно базового оффсета сегмента) в физическую позицию байта в `.log`. Запись индекса — восемь байт: четыре на оффсет, четыре на позицию.

Индекс **разреженный** и указывает только на **границы батчей**. Запись в индекс добавляется в момент дописывания батча, если с предыдущей записи индекса накопилось больше `index.interval.bytes` байт (по умолчанию 4096). Проверка делается один раз на батч, поэтому индекс получает не больше одной записи на батч.

Отсюда фактический шаг индекса: **примерно больший из двух — `index.interval.bytes` или размер батча.** При крупных батчах продюсера шаг равен их размеру. Полный индекс занимал бы слишком много памяти, а разреженного достаточно.

Поиск записи по оффсету:

1. бинарный поиск по именам файлов → нужный сегмент;
2. бинарный поиск в `.index` → ближайшая известная позиция **не позже** искомой;
3. последовательное чтение от этой позиции до нужного оффсета.

Третий шаг читает не больше, чем максимум из `index.interval.bytes` и размера одного батча. Поиск по-прежнему фактически константный, но константу задаёт продюсер своим `batch.size`: параметр, который выглядит чисто брокерским, на деле зависит от клиента.

### Когда индекс пустой

Если `index.interval.bytes` больше `segment.bytes`, сегмент закрывается раньше, чем условие успевает сработать. Файлы `.index` и `.timeindex` создаются, но после закрытия обрезаются до нуля.

Корректность не страдает: поиск по пустому индексу возвращает начало сегмента, дальше идёт последовательное чтение. Страдает стоимость — она становится равной размеру сегмента. На мегабайтном сегменте это незаметно, на гигабайтном — катастрофа, причём не только для случайного доступа: потребитель читает сегмент серией fetch-запросов, и каждый начинается с поиска, так что последовательное чтение сегмента становится квадратичным по его размеру.

### .timeindex — время в оффсет

Отображает timestamp в относительный оффсет. Работает так же разреженно. Используется для `offsetsForTimes()` (переиграть с конкретного момента — модуль 4) и для retention по времени.

Важная тонкость: `.timeindex` строится по **максимальному** таймстемпу батча и предполагает, что время неубывающее. При `CreateTime` и кривых часах клиента это предположение нарушается, и поиск по времени начинает врать.

## 6. Четыре оффсета партиции

Четыре разных числа, которые легко перепутать. Каждое отвечает на свой вопрос.

```
  удалено  │ видно всем        │ видно read_uncommitted │ не подтверждено
───────────┼───────────────────┼────────────────────────┼─────────────────
       log start             LSO                        HW               LEO
```

**Log Start Offset** — первый ещё существующий оффсет. Растёт при удалении сегментов по retention или при явном `DeleteRecords`. Запрос данных раньше него даёт `OffsetOutOfRangeException` — та самая ошибка, которую видит потребитель, отставший больше, чем на retention.

**High Watermark (HW)** — до какого оффсета записи реплицированы на все реплики из ISR. **Потребитель не видит ничего выше HW.** Это механизм, обеспечивающий, что читатель не увидит запись, которая может исчезнуть при смене лидера.

Запрос «последний оффсет» (ListOffsets с `latest`, он же `kafka-get-offsets.sh --time -1`) возвращает именно HW, а для `read_committed` — LSO, но не LEO. На одиночном брокере с RF=1 HW и LEO практически совпадают, разница появляется на кластере.

**Log End Offset (LEO)** — оффсет следующей записи, которая будет добавлена. То есть конец лога с точки зрения лидера.

**Last Stable Offset (LSO)** — граница для потребителей с `isolation.level=read_committed`: до этого оффсета все транзакции завершены. Незавершённая транзакция удерживает LSO, блокируя видимость всего, что за ней. Детали в модуле 6.

Разрыв между HW и LEO — это то, что уже записано лидером, но ещё не подтверждено фолловерами. Рост этого разрыва означает отстающую репликацию.

## 7. Retention: удаление по времени и размеру

Политика `cleanup.policy=delete` (по умолчанию).

### Параметры

| Параметр | Смысл | По умолчанию |
|---|---|---|
| `retention.ms` | хранить не дольше | 7 дней |
| `retention.bytes` | нижняя граница объёма партиции (см. ниже) | −1, без ограничения |
| `segment.ms` / `segment.bytes` | когда закрывать сегмент | 7 дней / 1 ГБ |
| `log.retention.check.interval.ms` | как часто проверять (брокер) | 5 минут |

`retention.bytes` считается **на партицию**, а не на топик. Топик с 12 партициями и `retention.bytes=1GB` займёт до 12 ГБ на реплику, то есть 36 ГБ при RF=3. Ошибка на порядок здесь стоит дорого.

### Как это работает на самом деле

Вот механика, которая объясняет вопрос из вступления.

Удаляются **только закрытые сегменты целиком**. Не записи. Проверка выглядит так: у сегмента берётся максимальный таймстемп; если он старше `retention.ms`, сегмент помечается на удаление.

Отсюда: запись живёт не `retention.ms`, а до тех пор, пока не выполнятся три условия подряд — сегмент закроется, весь сегмент устареет, и отработает проверка.

Пример. `retention.ms=60000`, `segment.bytes=1GB`, трафик небольшой. Активный сегмент будет заполняться неделю (до `segment.ms`), всё это время ни одна запись не удалится, хотя формально им «положено» жить минуту. На диске спокойно лежат данные недельной давности при retention в минуту.

Именно поэтому в учебных топиках `segment.ms` занижен до секунд — иначе эксперименты с retention невозможно наблюдать.

Практический вывод для продакшена: **`segment.ms` и `segment.bytes` должны быть согласованы с `retention.ms`.** Разумный ориентир — сегмент не длиннее десятой части retention.

### retention.bytes — нижняя граница, а не верхняя

Правило: брокер удаляет старейший закрытый сегмент, только если **после удаления** объём партиции — все сегменты, включая активный, — останется не меньше `retention.bytes`. Удаление останавливается, как только следующее увело бы партицию ниже лимита.

Пример: `retention.bytes=2 МБ`, `segment.bytes=1 МБ`. На диске остаются два закрытых сегмента и активный, около 3 МБ. Удали брокер ещё один — осталось бы меньше 2 МБ.

Практический вывод для планирования диска: **реальный объём партиции доходит до `retention.bytes + segment.bytes`.** При дефолтном сегменте в 1 ГБ и лимите в 1 ГБ это до двух гигабайт на партицию, вдвое больше, чем подсказывает название параметра. `retention.ms` устроен так же: запись живёт как минимум `retention.ms`, а сверху — на длину сегмента, интервал проверки и задержку удаления.

### Удаление это переименование

Помеченный сегмент сначала получает суффикс `.deleted`, и только через `log.segment.delete.delay.ms` (по умолчанию минута) файл действительно удаляется. Отсрочка нужна, чтобы не выдернуть файл из-под идущего чтения.

## 8. Compaction: свёртка по ключу

Политика `cleanup.policy=compact`. Принципиально другая идея: не «удалить старое», а «оставить по одной последней записи на каждый ключ».

Это техническая реализация перехода «поток → таблица» из модуля 1.

### Что гарантирует

- для любого ключа последнее значение сохраняется всегда;
- порядок записей не меняется;
- оффсеты не переприсваиваются — остаются дыры;
- потребитель, читающий с начала, увидит финальное состояние по каждому ключу.

### Чего не гарантирует

**Что в топике останется ровно одна запись на ключ.** Компакция асинхронна и работает не мгновенно. Грязная часть и активный сегмент (см. ниже) всегда могут содержать дубли. Это не баг, это нормальное рабочее состояние.

### Устройство

Партиция делится на три зоны, слева направо от старых записей к новым:

- **чистая часть** — уже скомпактирована, от начала лога до `firstDirtyOffset`;
- **грязная часть** — закрытые сегменты после последней компакции, здесь дубли;
- **активный сегмент** — компактор его не трогает никогда.

Граница `firstDirtyOffset` хранится в файле `cleaner-offset-checkpoint` в `log.dirs`.

В документации Kafka чистая часть называется tail, а грязная вместе с активным сегментом — head. Логика как у змеи: голова впереди, там, где лог растёт. Это обратно привычному «хвосту очереди», куда добавляют элементы, поэтому здесь используются термины «чистая» и «грязная».

Фоновый поток (log cleaner, `log.cleaner.threads`) строит карту «ключ → последний оффсет» по грязной части, затем переписывает **и грязную, и чистую** часть, выбрасывая записи, перекрытые картой. Чистая часть не заморожена: при каждой компакции она может уменьшиться.

### Когда запускается

| Параметр | Смысл | По умолчанию |
|---|---|---|
| `min.cleanable.dirty.ratio` | доля «грязного» от общего, при которой начинать | 0.5 |
| `min.compaction.lag.ms` | не трогать записи моложе | 0 |
| `max.compaction.lag.ms` | гарантированно скомпактить не позже | Long.MAX |
| `delete.retention.ms` | сколько хранить надгробия | 24 часа |

Отношение считается **на партицию и в байтах**:

```
ratio = грязная / (чистая + грязная)
```

Активный сегмент и записи моложе `min.compaction.lag.ms` в расчёт не входят. Если подходят несколько партиций, компактор берёт ту, у которой отношение выше. `max.compaction.lag.ms` работает поверх порога: запись, прождавшая дольше этого срока, форсирует компакцию независимо от отношения.

**Пример по шагам.** Запись 100 байт, сегмент закрывается каждые 10 записей, ключей три — A, B, C, порог 0.5.

| Шаг | Состояние | Расчёт | Действие |
|---|---|---|---|
| 1 | закрыты 0–9 и 10–19, активный 20–24, компакции не было | 2000 / (0 + 2000) = 1.0 | компакция |
| 2 | из 20 записей остались 3 (последние A, B, C), граница = 20 | чистая 300 байт | ждём |
| 3 | закрылся 20–29, активный 30–32 | 1000 / (300 + 1000) = 0.77 | компакция |
| 4 | новая карта перекрыла старые A, B, C в чистой части | чистая снова 300 байт, граница = 30 | ждём |

Если компакции ещё не было, чистая часть равна нулю и отношение сразу 1.0 — первый же закрытый сегмент компактится при первой возможности. На шаге 2 активный сегмент с записями 20–24 не тронут, хотя там наверняка есть A, B и C: потребитель, читающий с начала, в этот момент увидит дубли.

**Частоту задаёт кардинальность ключей.** При трёх ключах чистая часть крошечная, и компакция срабатывает почти на каждом новом сегменте. При миллионе уникальных ключей чистая часть остаётся, скажем, 100 МБ, и следующая компакция начнётся только после 100 МБ новых грязных данных. Немного ключей — компакция частая и дешёвая, много — редкая и дорогая.

**Зачем вообще порог.** Каждая компакция переписывает чистую часть целиком. Ниже порог — чаще компакция, меньше мусора, больше дискового ввода-вывода. Выше порог — реже компакция, но до следующего прохода на диске лежит больше дублей. При 0.5 до половины компактируемого объёма может быть мусором. В учебных экспериментах ставьте 0.01 — ради наблюдаемости, не ради эффективности.

**Почему в спокойном топике компакция может не запускаться неделями.** Причина не в отношении, а в активном сегменте: при `segment.ms` по умолчанию он закрывается раз в семь дней и только при очередной записи, а незакрытый сегмент компактору недоступен.

`max.compaction.lag.ms` важен для требований вида GDPR: он даёт верхнюю границу времени, за которое удаление гарантированно применится.

### Надгробия

Удаление ключа выражается записью с этим ключом и `value = null`. Это tombstone.

Компактор не может выбросить надгробие сразу: потребители, читающие с начала, должны его увидеть, иначе они не узнают об удалении. Поэтому надгробие живёт ещё `delete.retention.ms` после компакции и только потом исчезает.

Отсюда практическое требование: **потребитель compacted-топика обязан обрабатывать `null` как значение.** Если ваш десериализатор падает на null — он сломается на первом же удалении.

### Комбинированная политика

`cleanup.policy=compact,delete` — компактить и при этом удалять по retention. Применяется, когда таблица должна быть ещё и ограничена по времени: например, состояние сессий, где ключи старше суток не нужны вовсе.

Kafka Streams использует именно этот режим для windowed state stores.

## 9. Сколько делать партиций

Вопрос без универсального ответа, но с понятной методикой.

### Снизу: пропускная способность

```
партиций ≥ max(целевой_throughput / throughput_на_партицию_записи,
               целевой_throughput / throughput_на_партицию_чтения)
```

Пропускную способность одной партиции нужно **измерить на своём железе** (модуль 8), а не брать из статей. Она зависит от размера сообщения, сжатия, диска и RF.

### Снизу: параллелизм потребителей

В классических consumer-группах партиция — единица назначения. Потребителей в группе не может быть больше партиций: лишние простаивают. Нужно 20 параллельных обработчиков — нужно минимум 20 партиций.

Share groups (модуль 13) это ограничение снимают, но у них свои компромиссы.

### Сверху: стоимость

Каждая партиция это не бесплатно:

- **файловые дескрипторы**: минимум три файла на сегмент, умножить на число сегментов и партиций;
- **память на брокере**: буферы на каждую партицию;
- **время восстановления**: при отказе брокера контроллер выбирает лидера для каждой партиции отдельно;
- **задержка**: больше партиций — больше запросов и мельче батчи при том же трафике;
- **ребалансировка**: время назначения растёт с числом партиций.

### Практический ориентир

Начните с числа, кратного ожидаемому параллелизму потребителей, с запасом в два-три раза. Для учебных и небольших продовых топиков 6–12 партиций — разумная отправная точка. Тысячи партиций на топик — почти всегда ошибка проектирования.

И помните раздел 2: **увеличить можно, уменьшить нельзя, а увеличение ломает порядок по ключу.** Запас лучше, чем миграция.

## 10. Уровни конфигурации

Одна и та же настройка существует на двух уровнях с разными именами:

| Уровень брокера | Уровень топика |
|---|---|
| `log.retention.ms` | `retention.ms` |
| `log.segment.bytes` | `segment.bytes` |
| `log.cleanup.policy` | `cleanup.policy` |
| `log.roll.ms` | `segment.ms` |

Приоритет: значение на уровне топика перекрывает брокерское. Брокерское служит значением по умолчанию для новых топиков.

Топиковые настройки задаются при создании (`--config`) или меняются потом (`kafka-configs.sh --alter --entity-type topics`), применяются динамически, без перезапуска.

Полезная привычка: проверять действующее значение, а не предполагать его. `kafka-configs.sh --describe` покажет, откуда взялось значение — из дефолта, из брокерского конфига или из явной настройки топика.

## 13. F.A.Q.

Вопросы, возникшие при прохождении модуля. Где ответ уже изложен в теории, здесь дана короткая версия и ссылка на раздел.

### Что будет, если `segment.bytes` меньше `index.interval.bytes`?

В Kafka 4.x сделать `segment.bytes` меньше 4 КБ нельзя — минимум 1 МБ (раздел 4). Обратная ситуация достижима: поднять `index.interval.bytes` выше размера сегмента. Тогда индексы создаются, но остаются пустыми; корректность сохраняется, стоимость поиска становится равной размеру сегмента. Подробно — раздел 5, «Когда индекс пустой».

### `min.cleanable.dirty.ratio = 0.5` — половина от чего?

Не от сегмента и не от всего лога. От компактируемой части партиции в байтах: грязная часть делится на сумму чистой и грязной, активный сегмент не считается. Если компакции ещё не было, отношение сразу 1.0. Формула и пример по шагам — раздел 8.

### Почему скомпактированную часть называют «хвостом», если запись идёт в конец?

Терминология документации: tail — старая, чистая часть, head — новая, куда пишут; логика «голова впереди». Это противоположно «хвосту очереди». В этом курсе используются термины «чистая» и «грязная» часть — раздел 8.

### Что значат поля `count`, `size`, `valueSize` в выводе `kafka-dump-log.sh`?

Вывод читается в два уровня.

Строка батча:

| Поле | Значение |
|---|---|
| `baseOffset`, `lastOffset` | оффсеты первой и последней записи батча |
| `count` | число записей в батче, **не** размер |
| `position` | с какого байта файла `.log` начинается батч |
| `size` | размер батча на диске в байтах, с заголовком; для сжатого батча — в сжатом виде |
| `CreateTime` | максимальный таймстемп батча |
| `compresscodec` | алгоритм сжатия |
| `producerId` | идентификатор продюсера; не `-1` означает идемпотентный режим |
| `deleteHorizonMs` | связан с моментом, когда надгробие можно окончательно удалить |

Строки записей (с `--print-data-log`): `keySize` и `valueSize` — размер сериализованного ключа и значения конкретной записи в байтах. Для сжатого батча утилита распаковывает его, так что размеры несжатые.

Что стоит проверить руками:

- `position` следующего батча равен `position + size` текущего — эти же позиции записаны в `.index`;
- размер — это байты, не символы: кириллица в UTF-8 даёт по два байта на букву;
- у надгробия `valueSize: -1` — так формат кодирует отсутствие значения, в отличие от пустой строки с размером 0;
- после компакции `count` может быть меньше `lastOffset - baseOffset + 1`: записи выброшены, границы оффсетов батча остались.

### Почему шаг между записями `.index` около 16 КБ, а не 4 КБ?

Индекс указывает на границы батчей и получает не больше одной записи на батч. `kafka-producer-perf-test` с записями по 1000 байт и `batch.size=16384` собирает батчи около 16 КБ, поэтому шаг равен размеру батча. Правило — раздел 5.

### В лабе 2.7 индексы у закрытых сегментов есть, но пустые. Это нормально?

Да, это ожидаемый результат — раздел 5, «Когда индекс пустой». Открытый вопрос для самостоятельной проверки: откуда брокер возьмёт максимальный таймстемп закрытого сегмента с пустым `.timeindex` после перезапуска, и как это повлияет на retention по времени.

### На что влияет параметр `--time` в `kafka-get-offsets.sh`?

Он определяет, какую позицию запрашивать. Утилита отправляет запрос ListOffsets — тот же, что делает потребитель при старте или при `offsetsForTimes()`.

| Значение | Алиас | Что возвращает |
|---|---|---|
| `-2` | `earliest` | log start offset |
| `-1` | `latest` | high watermark (для `read_committed` — LSO), не LEO |
| `-3` | `max-timestamp` | оффсет записи с наибольшим таймстемпом (KIP-734) |
| `-4` | `earliest-local` | первый оффсет в локальном хранилище при tiered storage (KIP-1005) |
| `-5` | `latest-tiered` | последний оффсет, выгруженный в удалённое хранилище (KIP-1005) |
| число ≥ 0 | — | таймстемп в мс: первый оффсет с временем не меньше заданного |

Отрицательные значения — договорные константы протокола. Положительное — настоящий таймстемп, и брокер ищет его через `.timeindex`. Наличие алиасов в вашей версии проверяется через `--help`.

### Как читать команду вида `watch -n 2 "docker exec ... sh -c '...; ...'"`?

Три слоя снаружи внутрь:

1. `watch` раз в две секунды выполняет строку в двойных кавычках через `sh` на хосте. Обратный слеш в конце строки внутри двойных кавычек — перенос, он исчезает.
2. Хостовый `sh` запускает `docker exec ... sh -c '...'`; одинарные кавычки собирают обе команды в один аргумент.
3. `sh` внутри контейнера выполняет команды через `;` подряд.

`sh -c` внутри нужен, чтобы уложить две утилиты в один `docker exec` и чтобы точку с запятой разобрал shell контейнера, а не хоста.

### Почему при `retention.bytes=2 МБ` на диске остаются три сегмента, а не один активный?

Потому что `retention.bytes` — нижняя граница: брокер удаляет сегмент, только если после удаления объём партиции, включая активный сегмент, останется не меньше лимита. Раздел 7.

### Почему в лабе 2.10 сегмент не закрылся через 10 секунд после первой публикации?

Правило ролла — раздел 4. Проверять по порядку:

1. **Ролл случился, но выглядит иначе.** Закрытие не удаляет старый файл, рядом появляется новый. Два `.log` в каталоге — ролл был.
2. **Настройка не применилась.** Если топик существовал от прошлой попытки, `--create` упал с `TopicExistsException`, и `--config` никуда не записался. Проверка — `kafka-configs.sh --describe`.
3. **Разница таймстемпов не превысила `segment.ms`.** Сравнивается время записей, а не часы брокера. Проверка — `kafka-dump-log.sh ... | grep -o 'CreateTime: [0-9]*'`, разница первого и последнего значения.

### Почему `du -sh $DATA/m2.skew.v1-*` пишет «No such file or directory»?

Сама команда корректна: `$DATA` раскрывается на хосте, а `*` в двойных кавычках уходит в контейнер, где глоб раскрывает `sh`. Каталогов нет потому, что у образа `apache/kafka` `log.dirs` по умолчанию `/tmp/kraft-combined-logs`, а `/var/lib/kafka/data` — соглашение образов Confluent. Том был смонтирован в один каталог, а брокер писал в другой.

Последствие шире одной команды: данные жили в файловой системе контейнера, и любой `docker compose down`, даже без `-v`, их терял.

Исправление — явно задать каталог в `environment` обоих compose-файлов:

```yaml
KAFKA_LOG_DIRS: /var/lib/kafka/data
```

и сделать чистый старт с `down -v`. Проверка, что данные теперь в томе: `down` без `-v`, `up -d`, топики на месте.

Общий вывод: проверяйте действующее значение настройки у самого процесса (`kafka-configs.sh --describe --all`), а не полагайтесь на соглашения.

### Когда делать mini-broker?

После прохождения основного трека, отдельным репозиторием. Роадмап проекта будет расписан в конце.

## 14. Выводы по лабам

Короткая выжимка того, что показали эксперименты. Механика — в разделах 1–10, здесь только наблюдаемые факты и практические правила.

**2.1 CLI и конфигурация.** Действующее значение настройки имеет источник: `DEFAULT_CONFIG`, `STATIC_BROKER_CONFIG` или `DYNAMIC_TOPIC_CONFIG`; топиковое побеждает. Смотреть через `--describe --all`. Часть брокерских настроек меняется на лету, часть требует перезапуска — это указано в колонке Update Mode документации. Нарушение ограничений версии (KIP-1030) даёт `InvalidConfigurationException` сразу при `--alter`.

**2.2 Ключ и партиция.** Партиция вычисляется детерминированно: `toPositive(murmur2(key)) % n` в jshell совпадает с тем, что сделал брокер. Консьюмер выводит записи не в порядке отправки — партиции читаются независимо, но порядок внутри ключа сохранён. Записи без ключа на малом объёме ложатся в одну-две партиции (sticky), на большом выравниваются.

**2.3 Перекос партиций (поломка №1).** Ключ с низкой кардинальностью и неравномерным распределением даёт одну перегруженную партицию и пустые остальные. Диагностика без доступа к коду — `kafka-get-offsets.sh --time -1` по партициям и `du` каталогов. Увеличение числа партиций не лечит: одинаковый ключ всё равно попадёт в одну партицию. Лечится только сменой ключа, например составным.

**2.4 Изменение числа партиций.** После увеличения записи одного ключа оказываются в двух партициях, и их взаимный порядок перестаёт быть определён. Уменьшение отклоняется брокером.

**2.5 Сегменты.** Ролл по размеру предсказуем по объёму записи. Ролл по времени происходит только при следующей записи: простаивающая партиция не закрывает сегмент. Индекс активного сегмента предвыделен и большой, у закрытых обрезан.

**2.6 Файлы лога.** Единица хранения — батч; сжатие применяется к батчу целиком. Батчи консольного продюсера содержат по одной-несколько записей, у `kafka-producer-perf-test` — десятки. Шаг индекса равен размеру батча, если он больше `index.interval.bytes`.

**2.7 Пустой индекс.** При `index.interval.bytes` > `segment.bytes` индексы пустые, чтение корректно, стоимость поиска равна размеру сегмента.

**2.8 Retention.** Log start offset растёт скачками — ровно на размер удалённого сегмента. Реальное время жизни записи складывается из `retention.ms`, возраста сегмента, интервала проверки и задержки удаления. `retention.bytes` — нижняя граница: на диске до `retention.bytes + segment.bytes` на партицию.

**2.9 Потребитель за началом лога (поломка №2).** С `auto.offset.reset=none` — явное `OffsetOutOfRangeException`. Со значениями `earliest` или `latest` позиция сбрасывается **молча**, потеря данных для группы не видна без мониторинга. На алерт нужно ставить сравнение закоммиченного оффсета группы с log start offset, до того как retention догонит потребителя.

**2.10 Компакция и надгробия.** Для компакции нужен закрытый сегмент. После неё остаётся последняя версия ключа, в оффсетах появляются дыры, активный сегмент не тронут. Надгробие (`value = null`, в консольном продюсере через `null.marker`) видно потребителям ещё `delete.retention.ms` после компакции, потом исчезает. Потребитель, начавший читать после исчезновения надгробия, не узнает, что ключ существовал.

**2.11 Компакция не запускается (поломка №3).** При пороге 0.5 и малой доле грязных данных компактор корректно простаивает; отношение вычисляется по размерам `.log` и значению из `cleaner-offset-checkpoint`. `max.compaction.lag.ms` форсирует компакцию независимо от порога — это инструмент для требований вида «удалить данные не позже N часов».

**2.12 Надгробие ломает потребителя (поломка №4).** Код, не готовый к `null` в значении, падает на первом надгробии и при перезапуске падает на нём же бесконечно — это poison pill. Обработчик compacted-топика обязан явно решать, что делать с `null`: как правило, удалить ключ из своего хранилища.

**2.13 Расчёт числа партиций.** Метод: сначала найти, что упирается первым — запись в Kafka или обработка у потребителя, и считать число партиций от узкого места.

Для условий лабы (50 000 событий/с, 800 байт, 2 мс на запись, 3 дня, RF=3, рост ×3):

| Параметр | Значение |
|---|---|
| Поток | 40 МБ/с, ~3,5 ТБ в сутки |
| Хранение сейчас / через 2 года | ~31 ТБ / ~93 ТБ на кластер, без учёта сжатия |
| Партиций при потоке на партицию, загрузка 70% | 150 сейчас, 450 с учётом роста |
| Партиций при 20 ключах параллельно в потребителе | 8 сейчас, 24 с учётом роста |
| Трафик на партицию через 2 года (450 партиций) | ~270 КБ/с |
| `segment.ms` / `segment.bytes` | 6 часов / 1 ГБ |
| Узкое место | обработка у потребителя, не Kafka |

Три переносимых правила:

1. Число партиций считается от узкого места. Если узкое место — потребитель, ускорение потребителя уменьшает число партиций.
2. Потребителям нужен запас мощности: 100% загрузки в пике означает гарантированный рост лага при первом сбое. Ориентир — 60–70%.
3. Если порядок по ключу важен, число партиций выбирается один раз, с учётом роста.

Команды, использованные в практикуме. Общий справочник — [docs/commands.md](../commands.md).

### Переменные сессии

```bash
K="docker exec -i -e KAFKA_OPTS= kafka"
BS="localhost:9094"
BIN="/opt/kafka/bin"
DATA="/var/lib/kafka/data"
```

### Топики и конфигурация

```bash
# создать с настройками
$K $BIN/kafka-topics.sh --bootstrap-server $BS --create --topic T \
  --partitions 6 --replication-factor 1 --config segment.ms=15000

# описать, увеличить число партиций
$K $BIN/kafka-topics.sh --bootstrap-server $BS --describe --topic T
$K $BIN/kafka-topics.sh --bootstrap-server $BS --alter --topic T --partitions 12

# все настройки топика с источником значения
$K $BIN/kafka-configs.sh --bootstrap-server $BS --describe --entity-type topics --entity-name T --all

# изменить / удалить переопределение
$K $BIN/kafka-configs.sh --bootstrap-server $BS --alter --entity-type topics --entity-name T \
  --add-config retention.ms=3600000
$K $BIN/kafka-configs.sh --bootstrap-server $BS --alter --entity-type topics --entity-name T \
  --delete-config retention.ms

# динамическая настройка брокера
$K $BIN/kafka-configs.sh --bootstrap-server $BS --alter --entity-type brokers --entity-name 1 \
  --add-config log.cleaner.backoff.ms=5000
```

### Запись

```bash
# с ключами из stdin

  --bootstrap-server $BS --topic T --property parse.key=true --property key.separator=:

# надгробие
echo 'user-2:NULL' | $K $BIN/kafka-console-producer.sh --bootstrap-server $BS --topic T \
  --property parse.key=true --property key.separator=: --property null.marker=NULL

$K $BIN/kafka-producer-perf-test.sh --topic T --num-records 5000 --record-size 1000 \
```

```bash
# с начала, с партицией, оффсетом и ключом; не висеть бесконечно

  --timeout-ms 5000 --property print.key=true --property print.partition=true --property print.offset=true
```
