**Когда:** после модуля 4, перед модулем 5
**Время:** 10–14 часов
**Предварительно:** теория и практика модулей 3 и 4
**Результат:** Maven-модуль с вашим кодом, README с разделом «Решения», `notes/clients-own-code.md` с доказательствами приёмки

## Как устроен блок

Пять use case на одном домене. Каждый разобран так:

- **цель** — что должно получиться и зачем это бизнесу;
- **архитектура** — какие классы нужны, за что отвечает каждый, какие API Kafka он использует и почему ответственность вынесена именно так;
- **поток данных** — как запись проходит через классы;
- **этапы** — порядок работы. У каждого этапа: зачем он, что сделать, какие API и настройки задействованы, как проверить, что этап готов, и какие ошибки здесь делают чаще всего;
- **критерии приёмки** — финальная проверка use case;
- **решения для README** — вопросы, ответ на которые вы записываете своими словами.

Код здесь не дан ни строчкой. Имена классов — предложение, а не требование: можно назвать иначе и разбить по-другому, если в README объяснено почему. Обязательно другое — разделение ответственности и поведение.

### Правила

1. Во время работы не открывайте `ProducerProbe`, `ConsumerProbe`, `ManualCommitConsumer`, `ProducerModes`, `TenantPartitioner`, `LagReporter`. Источники — теория модулей 3 и 4, Javadoc `KafkaProducer`, `KafkaConsumer`, `Admin` и документация конфигурации.
2. Зонды и утилиты Kafka можно использовать для проверки — как генератор нагрузки или измеритель, — но не как образец.
3. Этап считается готовым только после проверки из его описания. Не переходите к следующему, пока проверка не прошла: ошибки нижних этапов в верхних почти не диагностируются.
4. Логика без Kafka — расчёт префикса, правила тревоги, разбор события — покрывается юнит-тестами (JUnit и AssertJ уже есть в `labs/pom.xml`). Логика с Kafka проверяется сценариями.

## Этап 0. Модуль и общие решения

### Зачем

Все пять use case живут в одном Maven-модуле и работают с одним топиком. Ключ записи и число партиций — решения, которые потом нельзя поменять без боли (модуль 2, разделы 2 и 9), поэтому они принимаются до первой строки кода.

### Что сделать

**Модуль.** Создайте `labs/own-clients` с собственным `pom.xml`:

- родитель — `labs`, как у `lab03-producer`;
- зависимость от `common` — оттуда `Env`, `OrderEvent`, `JsonSerde`; `kafka-clients` и логирование придут транзитивно;
- для UC-2 понадобится JDBC-драйвер встраиваемой базы — H2 (`com.h2database:h2`) или SQLite (`org.xerial:sqlite-jdbc`); добавите на этапе UC-2.

Добавьте модуль в `<modules>` в `labs/pom.xml`.

**Пакеты.** Предлагаемая раскладка:

| Пакет | Что там |
|---|---|
| `dev.learning.kafka.own.intake` | UC-1, приём заказов |
| `dev.learning.kafka.own.processing` | UC-2, обработка заказов |
| `dev.learning.kafka.own.replay` | UC-3, переигровка |
| `dev.learning.kafka.own.fraud` | UC-4, тяжёлая обработка |
| `dev.learning.kafka.own.lag` | UC-5, наблюдение за отставанием |

Общий код между use case не выносите заранее. Если что-то понадобится в двух местах — тогда и вынесете.

**Решения.** Запишите в `labs/own-clients/README.md`, раздел «Общие решения»:

- **ключ записи.** Требование бизнеса: события одного продавца обрабатываются по порядку. Что тогда ключ — `orderId` или `sellerId`? Учтите, что Javadoc `OrderEvent` в `common` предлагает `orderId` — объясните, почему ваше требование важнее;
- **число партиций.** Пик 2000 заказов в секунду, до 8 обработчиков. Посчитайте по методу модуля 2 и выберите число с хорошей делимостью (М4, F.A.Q. и раздел 2);
- **`acks` и `min.insync.replicas`.** Что на учебном одиночном брокере и что было бы в продакшене с RF=3 (М3, раздел 5).

Создайте топик:

```bash
$K $BIN/kafka-topics.sh --bootstrap-server $BS --create --topic orders.created.v1 \
  --partitions <ваше число> --replication-factor 1
```

### Проверка

```bash
cd labs
mvn -q -pl own-clients -am install -DskipTests
```

Собирается без ошибок, топик существует с выбранным числом партиций.

### Типичные ошибки

- модуль не добавлен в `<modules>` — `-pl own-clients` его не найдёт;
- версия `kafka-clients` указана в модуле заново — она должна приходить из родителя, иначе модули разъедутся по версиям.

## UC-1. Приём заказов

### Цель

Сервис принимает заказы от витрины и публикует их в `orders.created.v1`. Витрину имитирует встроенный генератор. Главное требование: **принятый заказ не исчезает молча.** Для каждого заказа можно доказать его судьбу — подтверждён брокером или не отправлен, с причиной.

### Архитектура

| Класс | Отвечает за | API Kafka | Почему отдельно |
|---|---|---|---|
| `IntakeApp` | точка входа: читает параметры, собирает компоненты, регистрирует shutdown hook, задаёт порядок остановки | — | сборка и порядок жизненного цикла в одном месте, остальные классы о них не знают |
| `OrderGenerator` | создаёт `OrderEvent` с заданной скоростью и передаёт в публикатор | — | имитация витрины; в реальном сервисе здесь был бы HTTP-контроллер, и остальной код не изменился бы |
| `OrderPublisher` | владеет единственным `KafkaProducer`: конфигурация, отправка, закрытие | `KafkaProducer`, `ProducerRecord`, `send(record, callback)`, `close(Duration)` | вся конфигурация гарантий в одном месте; продюсер один на сервис (М3, раздел 12) |
| `PublishCallback` | реакция на результат отправки конкретного заказа | `Callback`, `RecordMetadata`, иерархия исключений | у каждого заказа своя судьба; callback знает, какой заказ он сопровождает |
| `DeliveryJournal` | хранит судьбу заказов: принят, подтверждён, не отправлен с причиной | — | доказательство отсутствия тихих потерь; запись на диск не должна идти в Sender-потоке |
| `CountingInterceptor` | счётчики отправленных, подтверждённых и неудачных записей | `ProducerInterceptor` | наблюдение на уровне клиента, независимо от кода приложения |

### Поток данных

```
OrderGenerator ──accept──▶ OrderPublisher ──send(record, callback)──▶ KafkaProducer
                               │                                          │
                               └── journal.accepted(orderId)              │ Sender-поток
                                                                          ▼
                     DeliveryJournal ◀──acked / failed── PublishCallback.onCompletion
                           │
                           └── очередь ──▶ поток записи на диск
```

### Этап 1.1. Публикатор с явной конфигурацией

**Зачем.** Гарантии продюсера зависят от нескольких настроек сразу, и часть из них молча меняет другие (М3, лаба 3.5). Первым делом конфигурация, которую нельзя ослабить случайно.

**Что сделать.** `OrderPublisher` создаёт `KafkaProducer<String, OrderEvent>`. Сериализатор ключа — `StringSerializer`, значения — `JsonSerde.serializer()` из `common`. Настройки задаются явно, даже если совпадают с умолчанием:

| Настройка | Почему явно |
|---|---|
| `enable.idempotence=true` | явное значение превращает противоречие в ошибку старта (М3, раздел 8) |
| `acks=all` | гарантия записи (М3, раздел 5) |
| `delivery.timeout.ms` | предел жизни записи в продюсере (М3, раздел 6); выбор — в решениях |
| `max.block.ms` | предел ожидания внутри `send()` (М3, раздел 2); выбор — в решениях |
| `linger.ms`, `batch.size` | под нагрузку 500–2000 в секунду, по замерам модуля 3 |

`IntakeApp` пока только создаёт публикатор и закрывает его.

**Проверка.** Запустите с `acks=1`, переданным параметром, — сервис должен упасть на старте с `ConfigException`. Это сразу закрывает AC1.5.

**Типичные ошибки.** Продюсер создаётся на каждую отправку; `enable.idempotence` не задан явно — тогда `acks=1` пройдёт молча.

### Этап 1.2. Генератор и отправка с callback

**Зачем.** Минимальный рабочий поток: заказы уходят в топик асинхронно.

**Что сделать.**

- `OrderGenerator` в своём потоке создаёт заказы с заданной скоростью: уникальный `orderId`, `sellerId` из ~1000 значений с неравномерным распределением, сумма, время создания. Темп держится по расписанию от момента старта, а не паузой после каждого заказа: иначе время отправки добавляется к паузе, и скорость плывёт;
- `OrderPublisher.accept(order)` строит `ProducerRecord` с выбранным ключом и вызывает `send(record, callback)`;
- `PublishCallback` пока только считает успехи и ошибки.

**API.** `send()` не ждёт брокера — он кладёт запись в буфер и сразу возвращает управление (М3, раздел 1). Callback вызывается позже, в Sender-потоке.

**Проверка.** 500 заказов в секунду в течение минуты. Сумма конечных оффсетов по партициям (`kafka-get-offsets.sh --time -1`) равна числу отправленных. Ошибок ноль.

**Типичные ошибки.** `send().get()` в генераторе — пропускная способность упадёт на порядки (М3, лаба 3.1); одна общая `Callback` без ссылки на заказ — потом не узнать, какой заказ не ушёл.

### Этап 1.3. Журнал судьбы заказов

**Зачем.** Требование «ни один заказ не исчезает молча» нужно уметь доказать. Для этого у каждого заказа должна быть зафиксирована судьба: принят → подтверждён или принят → не отправлен с причиной.

**Что сделать.**

- `DeliveryJournal` с тремя операциями: `accepted(orderId)`, `acked(orderId, partition, offset)`, `failed(orderId, reason)`;
- `accepted` вызывается **до** `send()`: если сервис упадёт после `send()`, заказ всё равно останется в журнале;
- `PublishCallback` вызывает `acked` или `failed`;
- запись на диск выполняет **отдельный поток**: операции журнала только кладут строку в очередь. Callback выполняется в Sender-потоке, и запись в файл прямо оттуда тормозит отправку всех партиций (М3, раздел 9; лаба 3.9);
- формат — три файла с одним идентификатором на строку, чтобы сверять через `sort` и `comm`, как в лабах.

**Проверка.**

```bash
sort -u accepted.log | wc -l
sort -u acked.log | wc -l
comm -23 <(sort -u accepted.log) <(sort -u acked.log) | wc -l     # принятые без подтверждения
```

После минуты при 500 заказах в секунду последняя команда даёт 0.

**Типичные ошибки.** Запись в файл прямо в callback; `accepted` после `send()` — при падении между ними заказ пропадёт из журнала; очередь журнала неограниченная без счётчика её размера — при медленном диске она станет утечкой памяти незаметно.

### Этап 1.4. Классификация ошибок

**Зачем.** Когда callback получил исключение, клиент уже исчерпал свои ретраи (М3, раздел 6). Ваш код не повторяет — он решает, что записать в причину и имеет ли смысл переотправка.

**Что сделать.** В `PublishCallback` разделите:

| Класс ошибки | Примеры | Что значит для переотправки |
|---|---|---|
| ретраибельная, исчерпан `delivery.timeout.ms` | `TimeoutException` | **результат неизвестен**: заказ мог дойти (М3, лаба 3.8); переотправка возможна, но может дать дубль |
| окончательная | `RecordTooLargeException`, `SerializationException`, ошибки авторизации | повторять бессмысленно, нужна правка заказа или конфигурации |

Базовый класс ретраибельных ошибок — `RetriableException`. Причина в журнале должна позволять различить эти случаи.

**Проверка.** Отправьте заказ, сериализованный размер которого больше `max.request.size`, — например, с огромной строкой в поле `tenant`. Он должен оказаться в `failed.log` с причиной «окончательная», без повторов.

**Типичные ошибки.** Повтор `send()` из callback — это новая запись с новым номером последовательности, идемпотентность её не узнает (М3, F.A.Q.); вызов `send()` из callback вообще — callback в Sender-потоке.

### Этап 1.5. Интерсептор

**Зачем.** Счётчики на уровне клиента, которые не зависят от вашего кода: если приложение где-то потеряет ошибку, интерсептор её всё равно увидит.

**Что сделать.**

- `CountingInterceptor` реализует `ProducerInterceptor<String, OrderEvent>`: `onSend` — отправлено, `onAcknowledgement` — подтверждено или ошибка, по наличию исключения;
- подключается через настройку `interceptor.classes` — экземпляр создаёт сам клиент, а не вы;
- отсюда вопрос дизайна: как вывести счётчики, если ссылки на экземпляр у вас нет? Варианты — интерсептор сам печатает их по таймеру, запущенному в `configure()` и остановленному в `close()`; или публикует в общий реестр. Выберите и обоснуйте;
- `onSend` выполняется в потоке приложения, `onAcknowledgement` — в Sender-потоке. Оба должны быть мгновенными.

**Проверка.** После минуты при 500 заказах в секунду счётчики интерсептора совпадают с числами журнала.

**Типичные ошибки.** Счётчики на `int` или `long` без синхронизации — `onSend` и `onAcknowledgement` в разных потоках; `onSend` возвращает `null` — запись пропадёт.

### Этап 1.6. Заполненный буфер

**Зачем.** При недоступном брокере буфер заполняется, и `send()` начинает блокировать поток генератора — в реальном сервисе это поток обработки HTTP-запроса (М3, раздел 2).

**Что сделать.**

- выберите `max.block.ms` — сколько витрина готова ждать ответа;
- запомните из лабы 3.7: ошибки ожидания по `max.block.ms` не бросаются из `send()`, а приходят в callback, вызванный **в потоке генератора внутри `send()`**. Ваш callback должен их корректно отработать — это отказ в приёме, а не ошибка доставки;
- `send()` всё же может бросить исключение синхронно — при ошибке сериализации или закрытом продюсере. Обработайте и этот путь: заказ уже записан в журнал как принятый, его судьба должна быть зафиксирована;
- отказы в приёме считайте отдельно и выводите.

**Проверка.** AC1.4: маленький `buffer.memory`, пауза брокера, как в лабе 3.7.

**Типичные ошибки.** Обработка только синхронных исключений `send()` — отказы по памяти пройдут мимо.

### Этап 1.7. Штатная остановка

**Зачем.** При остановке во время потока часть заказов принята, но ещё в буфере. Если просто выйти, они пропадут без следа.

**Что сделать.** Порядок остановки в shutdown hook — его и нужно продумать:

1. генератор прекращает принимать новые заказы;
2. `producer.close(Duration)` — клиент дожидается отправки буфера, все callback отрабатывают;
3. журнал дописывает очередь на диск и закрывается.

Подумайте, что будет при обратном порядке шагов 2 и 3 и что — если таймаут `close` истечёт раньше, чем буфер отправится.

**Проверка.** AC1.6.

**Типичные ошибки.** `close()` без таймаута при недоступном брокере — остановка зависнет до `delivery.timeout.ms`; журнал закрыт раньше продюсера — последние callback пишут в закрытый журнал.

### Критерии приёмки UC-1

| ID | Как воспроизвести | Ожидаемый результат | Доказательство |
|---|---|---|---|
| AC1.1 | 5 минут при 500 заказах/с, затем минута при 2000/с | ноль ошибок; заказов в топике столько же, сколько принято | журнал, счётчики интерсептора, `kafka-get-offsets.sh` |
| AC1.2 | `docker pause kafka` на 10 с во время потока | ноль неотправленных; все принятые — в топике | журнал + сверка с топиком |
| AC1.3 | пауза брокера дольше `delivery.timeout.ms` (лаба 3.8) | каждый недоставленный заказ в `failed.log`; их число равно `record-error-total`; вы показываете, какие из них всё-таки в топике | сверка множеств |
| AC1.4 | маленький `buffer.memory` и пауза брокера (лаба 3.7) | блокировка не дольше `max.block.ms`; отказы видны в счётчиках сервиса | вывод счётчиков |
| AC1.5 | запуск с `acks=1` | сервис не стартует | вывод запуска |
| AC1.6 | SIGTERM при 500 заказах/с | у каждого принятого заказа есть судьба | `comm` по журналу |

Сверка журнала с топиком — идентификаторы заказов из топика:

```bash
$K $BIN/kafka-console-consumer.sh --bootstrap-server $BS --topic orders.created.v1 \
  --from-beginning --timeout-ms 15000 2>/dev/null \
  | grep -o '"orderId":"[^"]*"' | cut -d'"' -f4 | sort -u > /tmp/in-topic.txt
```

### Решения для README

- как журнал не замедляет Sender-поток, и что будет при медленном диске;
- значения `max.block.ms` и `delivery.timeout.ms` и от чего они зависят в продакшене;
- `linger.ms` и `batch.size` — с опорой на замеры модуля 3;
- как вывести счётчики интерсептора, если его создаёт клиент;
- кто и как переотправит неотправленные заказы, и почему переотправка может дать дубль.

## UC-2. Обработка заказов

### Цель

Обработчик читает `orders.created.v1` и по каждому заказу прибавляет сумму к балансу продавца. Повторная обработка удвоит сумму — поэтому **баланс должен быть верным при любых сбоях и ребалансировках.** Доставка — at-least-once, результат — effectively-once (М4, раздел 5).

### Архитектура

| Класс | Отвечает за | API Kafka | Почему отдельно |
|---|---|---|---|
| `ProcessorApp` | точка входа, shutdown hook с `wakeup()`, ожидание завершения основного потока | `KafkaConsumer.wakeup()` | только `wakeup()` можно вызвать из другого потока (М4, раздел 1) |
| `ProcessingLoop` | цикл `poll()`: разбор, обработка, учёт оффсетов, коммит | `subscribe`, `poll`, `commitAsync`, `commitSync`, `close` | всё взаимодействие с потребителем — в одном потоке и одном классе |
| `OrderParser` | превращает значение записи в `OrderEvent` или сообщает, что запись битая | — | разбор отделён от потребителя, чтобы битая запись не останавливала `poll()` |
| `BalanceStore` | баланс продавцов и учёт обработанных заказов в одной транзакции | JDBC | идемпотентность обеспечивается хранилищем, а не памятью процесса |
| `OffsetTracker` | оффсеты следующих записей по обработанному, для назначенных партиций | `TopicPartition`, `OffsetAndMetadata` | что коммитить — отдельное знание, нужное и циклу, и listener'у |
| `RebalanceHandler` | реакция на отзыв, назначение и потерю партиций | `ConsumerRebalanceListener` | у каждого метода свой контракт (М4, раздел 9) |
| `PoisonLog` | фиксирует битые записи: партиция, оффсет, сырое значение | — | битая запись не теряется без следа |

### Поток данных

```
poll() ──▶ ConsumerRecords
              │ для каждой записи
              ▼
         OrderParser ──битая──▶ PoisonLog
              │ OrderEvent
              ▼
         BalanceStore.apply(order)   ← одна транзакция: «заказ обработан?» + баланс
              │
              ▼
         OffsetTracker.done(partition, offset + 1)
              │ после пачки
              ▼
         commitAsync(tracker.snapshot())

RebalanceHandler:  revoked → commitSync(отзываемые) → tracker.remove
                   lost    → tracker.remove, без коммита
```

### Этап 2.1. Хранилище с идемпотентным применением

**Зачем.** Идемпотентность — свойство результата, а не потребителя. Если она есть в хранилище, все сбои Kafka сводятся к «запись пришла ещё раз», и это безопасно. Поэтому хранилище — первым, до Kafka.

**Что сделать.**

- добавьте в `pom.xml` модуля JDBC-драйвер H2 или SQLite;
- две таблицы: балансы продавцов и обработанные заказы, где идентификатор заказа — первичный ключ;
- операция `apply(order)` в **одной транзакции**: попытаться отметить заказ как обработанный; если он уже есть — ничего не менять и сообщить «повтор»; если нет — прибавить сумму к балансу;
- почему одна транзакция: если отметка и баланс пишутся раздельно, сбой между ними даст либо потерянную сумму, либо двойную.

**Проверка.** Юнит-тест: применить один заказ дважды — баланс изменился один раз, второе применение вернуло «повтор». Применить два разных заказа одного продавца — баланс равен сумме.

**Типичные ошибки.** Проверка «уже обработан?» отдельным запросом перед вставкой — два экземпляра обработчика могут пройти проверку одновременно; идентификатор обработанного хранится в памяти — после перезапуска он забыт.

### Этап 2.2. Цикл poll без коммита

**Зачем.** Убедиться, что потребитель читает и разбирает записи, прежде чем добавлять сложность.

**Что сделать.**

- `KafkaConsumer<String, String>` — значение как строка. Разбор в `OrderParser`, а не десериализатором: если десериализатор бросит исключение, его бросит `poll()`, и позиция не сдвинется — потребитель будет спотыкаться об одну и ту же запись. Разбор в своём коде даёт контроль над битыми записями;
- явно: `group.protocol=consumer`, `enable.auto.commit=false`, `auto.offset.reset` — выбор с обоснованием (М4, раздел 4);
- `subscribe` пока без listener'а;
- цикл: `poll(Duration)`, для каждой записи — разбор и `apply`, счётчики.

**Проверка.** UC-1 пишет минуту. Обработчик читает, сумма балансов в хранилище равна сумме заказов.

**Типичные ошибки.** Создание `KafkaConsumer` в одном потоке, а `poll()` в другом; `group.protocol` не задан — получите `classic` (М4, раздел 8).

### Этап 2.3. Ручной коммит

**Зачем.** Без коммита каждый перезапуск начинает с начала — повторов много, хотя баланс и защищён. Коммит сокращает повторы до одной пачки.

**Что сделать.**

- `OffsetTracker` хранит для каждой партиции оффсет **следующей** записи после последней обработанной (М4, раздел 3);
- после обработки пачки — `commitAsync(tracker.snapshot())`;
- почему асинхронный в цикле и что делать с его ошибками — М4, раздел 3: пропущенный коммит перекроется следующим.

**Проверка.** Обработать минуту записей, остановить через Ctrl+C, запустить снова без новых записей. Число повторов — те, что попали между последним коммитом и остановкой. Закоммиченный оффсет в `kafka-consumer-groups.sh --describe` совпадает с концом партиций или отстаёт не больше чем на одну пачку.

**Типичные ошибки.** Коммит `offset` вместо `offset + 1`; коммит `consumer.position()` вместо обработанного — позиция может быть впереди обработки.

### Этап 2.4. Listener

**Зачем.** При ребалансировке партиция уходит к другому экземпляру. Всё, что обработано, но не закоммичено, новый владелец обработает повторно (М4, лаба 4.7).

**Что сделать.** `RebalanceHandler`, передаётся в `subscribe`:

| Метод | Действие | Почему |
|---|---|---|
| `onPartitionsRevoked` | `commitSync` оффсетов **отзываемых** партиций, затем убрать их из трекера | последний момент закоммитить, пока партиция ваша |
| `onPartitionsLost` | только убрать из трекера | партиции уже у других, коммит затрёт их прогресс |
| `onPartitionsAssigned` | залогировать | если оффсеты храните ещё и в базе — здесь `seek` на оффсет из базы (решение для README) |

Все методы вызываются внутри `poll()` в потоке цикла — поэтому `consumer` в них использовать можно.

**Проверка.** AC2.3.

**Типичные ошибки.** Коммит всех оффсетов трекера в `onPartitionsRevoked`, а не только отзываемых; коммит в `onPartitionsLost`.

### Этап 2.5. Штатная остановка

**Зачем.** Без штатной остановки каждая остановка — как `kill -9`: повторы и ожидание таймаута сессии остальными членами группы.

**Что сделать.**

- shutdown hook вызывает `consumer.wakeup()` и ждёт, пока основной поток завершится;
- `poll()` или блокирующий коммит в основном потоке бросит `WakeupException` — это сигнал выхода, а не ошибка;
- при выходе — `commitSync` трекера, затем `close()`; `close()` вызовет `onPartitionsRevoked` для всех партиций (М4, раздел 9).

**Проверка.** AC2.6.

**Типичные ошибки.** `WakeupException` пойман общим `catch (Exception)` и цикл продолжается; shutdown hook не ждёт основной поток — JVM завершится до коммита.

### Этап 2.6. Битые записи

**Зачем.** Одна запись, которую нельзя разобрать, не должна останавливать обработку навсегда — и не должна исчезнуть без следа.

**Что сделать.**

- `OrderParser` возвращает результат «разобрано» или «битая», без исключения наружу;
- битая запись — в `PoisonLog` с партицией и оффсетом, и её оффсет учитывается в трекере как обработанный, чтобы не перечитывать её бесконечно;
- в модуле 10 это станет топиком мёртвых писем; сейчас — файл.

**Проверка.** AC2.5.

### Этап 2.7. Бюджет poll и приёмка

**Зачем.** Обработка 2 мс в среднем и 20 мс в пике. Нужно убедиться, что при пике экземпляр не выбывает из группы (М4, раздел 6).

**Что сделать.** Добавьте параметр искусственной задержки обработки. Посчитайте: `max.poll.records × 20 мс` против `max.poll.interval.ms`. Запишите расчёт и выбранные значения в README.

**Проверка.** AC2.4, затем AC2.1 и AC2.2.

## UC-3. Переигровка заказов за период

### Цель

Инструмент выгружает все заказы, принятые в заданный интервал времени, из всех партиций топика — например, чтобы перепроверить заказы за время ошибки другого сервиса. Он не входит ни в какую группу и не трогает рабочие группы.

### Архитектура

| Класс | Отвечает за | API Kafka | Почему отдельно |
|---|---|---|---|
| `ReplayApp` | параметры: топик, «с», «по», файл; запуск | — | — |
| `ReplayPlanner` | для каждой партиции вычисляет начало и границу чтения | `partitionsFor`, `offsetsForTimes`, `beginningOffsets`, `endOffsets` | план можно вывести и проверить до чтения |
| `BoundedReader` | читает партиции от начала до границы, фильтрует по времени | `assign`, `seek`, `poll`, `position` | чтение отделено от планирования |
| `ReplayWriter` | пишет записи в файл | — | — |

`ReplayPlanner` и `BoundedReader` могут использовать один `KafkaConsumer` — без `group.id`.

### Поток данных

```
partitionsFor(topic) ──▶ список партиций
offsetsForTimes(«с»)  ──▶ начало по каждой партиции (или null)
endOffsets()          ──▶ граница на момент запуска
beginningOffsets()    ──▶ log start offset — для проверки потери начала
         │ план
         ▼
assign(партиции с началом) → seek(начало) → poll до границы → фильтр по времени → файл
```

### Этап 3.1. План

**Зачем.** Вся логика «откуда и докуда» — в плане. Если план неверен, чтение бесполезно, а проверить план можно без единой выгруженной записи.

**Что сделать.**

- потребитель **без** `group.id` и с `enable.auto.commit=false`: инструмент не участвует ни в каких группах (М4, раздел 11);
- `offsetsForTimes` для каждой партиции со временем «с». Значение `null` означает, что в партиции нет записей не раньше этого времени — партиция пропускается (C1);
- граница — `endOffsets` на момент запуска: всё, что запишут позже, выгружаться не будет (C2);
- потеря начала интервала (C3) — придумайте, как определить по `beginningOffsets`, найденному началу и времени первой записи. Подумайте, почему это можно определить только с оговорками;
- выведите план таблицей: партиция, начало, граница.

**Проверка.** Сравните начало с `kafka-get-offsets.sh --time <мс>` для того же времени — должно совпасть.

**Типичные ошибки.** `group.id` оставлен из `Env` — тогда инструмент — член группы с этим именем; граница вычисляется заново на каждом шаге — при непрерывной записи чтение не закончится.

### Этап 3.2. Ограниченное чтение

**Зачем.** Прочитать ровно план и завершиться.

**Что сделать.**

- `assign` только партиций с найденным началом, `seek` на начало;
- `poll` в цикле; запись берётся, только если её время в интервале;
- партиция считается дочитанной, когда её позиция дошла до границы — а не когда `poll` вернул пусто: пустой ответ значит «пока ничего не пришло», а не «больше ничего нет»;
- дочитанные партиции можно снять с чтения через `pause` или новый `assign` — решите сами;
- инструмент завершается, когда дочитаны все.

Отдельный вопрос — конец интервала. Время записи при `CreateTime` задаёт продюсер, и в партиции оно не обязано расти строго монотонно (М2, раздел 3). Поэтому «остановиться на первой записи позже конца интервала» может пропустить записи. Решите, как обходиться с этим, и запишите.

**Проверка.** AC3.1–AC3.3.

### Критерии приёмки UC-3

| ID | Как воспроизвести | Ожидаемый результат | Доказательство |
|---|---|---|---|
| AC3.1 | три волны записей с паузами по минуте; выгрузить среднюю | в файле ровно записи средней волны | сверка с `kafka-console-consumer.sh --property print.timestamp=true` |
| AC3.2 | одна партиция не получала записей в третьей волне; выгрузить третью | инструмент завершается без ошибки | вывод |
| AC3.3 | UC-1 пишет во время выгрузки | инструмент завершается; в файле нет записей, созданных после запуска | время завершения + сверка |
| AC3.4 | топик с `retention.ms` в 1 минуту, интервал начинается раньше удалённого | выгружено то, что есть, и сообщение о потере начала | вывод |

Для AC3.1 нужен генератор, которому можно задать число заказов. Если в UC-1 его нет, используйте `ProducerProbe` в другой топик того же формата — или добавьте параметр в UC-1.

### Решения для README

- чем `offsetsForTimes` + `seek` лучше `kafka-consumer-groups.sh --reset-offsets` для этой задачи;
- почему пустой `poll()` не означает конец партиции;
- как обрабатывается немонотонное время записей;
- как определяется потеря начала интервала и где это определение ошибается.

## UC-4. Тяжёлая обработка

### Цель

Каждому заказу нужна антифрод-проверка во внешнем сервисе: 50–200 мс, в среднем 100. Проверять нужно 500 заказов в секунду на одном экземпляре. Порядок по продавцу сохраняется. Здесь сходится всё самое сложное в потребителе: пул, обратное давление, коммит только надёжного прогресса (М4, разделы 11 и 12).

### Расчёт до начала

Запишите в README:

- сколько заказов в секунду проверит один экземпляр, если проверять последовательно в потоке `poll()`;
- сколько экземпляров понадобилось бы при модели «потребитель на поток», и хватит ли партиций из этапа 0;
- сколько проверок должно идти одновременно в одном экземпляре, чтобы держать 500 в секунду с запасом.

От этого расчёта зависят размеры пула и очереди.

### Архитектура

| Класс | Отвечает за | API Kafka | Почему отдельно |
|---|---|---|---|
| `FraudApp` | точка входа, остановка | `wakeup()` | — |
| `FraudCheckService` | имитация внешнего вызова: задержка в заданных пределах | — | подменяемая зависимость |
| `OrderedExecutor` | параллельное выполнение с сохранением порядка по продавцу: N однопоточных исполнителей, продавец всегда попадает в один и тот же | — | порядок по ключу при параллельности (М4, раздел 12) |
| `CommitTracker` | для каждой партиции — какие оффсеты в работе, какие готовы, и до какого оффсета всё готово подряд | — | чистая логика, проверяется юнит-тестами |
| `DispatchLoop` | поток `poll()`: раздаёт записи, решает про паузу, коммитит готовый префикс | `poll`, `pause`, `resume`, `paused`, `assignment`, `commitAsync` | **единственный поток, который трогает потребитель** |
| `RebalanceHandler` | что делать с задачами отзываемых партиций | `ConsumerRebalanceListener` | — |

### Главное ограничение дизайна

`KafkaConsumer` не потокобезопасен. Проверки завершаются в потоках пула, но коммит, `pause` и `resume` можно вызывать **только** из потока `poll()`. Поэтому потоки пула лишь отмечают «готово» в потокобезопасной структуре `CommitTracker`, а поток `poll()` на каждом витке читает её и действует. Этот принцип определяет всё остальное.

### Поток данных

```
DispatchLoop (поток poll)                       OrderedExecutor (N потоков)
  poll() ──▶ записи
    │  tracker.started(p, offset)
    └──▶ execute(sellerId, задача) ─────────────▶ FraudCheckService.check(order)
                                                        │
  на каждом витке:                                      │ tracker.completed(p, offset)
    в очереди больше порога? → pause(assignment)  ◀─────┘
    меньше нижнего порога?   → resume(paused)
    commitAsync(tracker.committable())
```

### Этап 4.1. Внешний сервис и упорядоченный пул — без Kafka

**Зачем.** Порядок по ключу при параллельной обработке — отдельная задача. Её проще решить и проверить без потребителя.

**Что сделать.**

- `FraudCheckService.check(order)` — задержка случайной длины в заданных пределах;
- `OrderedExecutor` — N однопоточных исполнителей; номер исполнителя вычисляется из ключа, поэтому задачи одного продавца выполняются в одном потоке по очереди, а разных продавцов — параллельно;
- у каждого исполнителя **ограниченная** очередь; общий счётчик задач в очередях и в работе.

Подумайте о цене этого решения: медленная проверка одного продавца задерживает всех продавцов того же исполнителя.

**Проверка.** Юнит-тест: 10 000 задач по 100 продавцам — для каждого продавца порядок выполнения совпадает с порядком отправки; при N = 50 и задержке 100 мс 10 000 задач выполняются примерно за 20 секунд.

**Типичные ошибки.** Обычный пул на N потоков — порядок по продавцу теряется; неограниченные очереди.

### Этап 4.2. Готовый префикс

**Зачем.** Записи 40, 41, 42 одной партиции проверяются параллельно. Если 42 закончилась первой, коммит 43 объявит 40 и 41 обработанными — при падении они потеряются (М4, раздел 12).

**Что сделать.** `CommitTracker` для каждой партиции:

- `started(offset)` — запись отдана в работу;
- `completed(offset)` — проверка завершена;
- `committable()` — оффсет, до которого **все** записи завершены, плюс один.

Идея вычисления: наименьший оффсет среди ещё не завершённых — это и есть граница. Если незавершённых нет — граница на единицу больше последнего отданного. Структуру данных выберите сами; учтите, что `completed` вызывается из потоков пула, а `committable` — из потока `poll()`.

**Проверка.** Юнит-тесты:

- `started` 40, 41, 42; `completed` 42 → граница 40;
- затем `completed` 40 → граница 41;
- затем `completed` 41 → граница 43;
- ни одной незавершённой → граница = последний отданный + 1.

**Типичные ошибки.** Коммит максимального завершённого оффсета; граница считается без учёта записей, ещё не отданных в работу.

### Этап 4.3. Цикл раздачи без обратного давления

**Зачем.** Собрать поток целиком и увидеть, почему без паузы он ломается.

**Что сделать.** `DispatchLoop`: `poll`, для каждой записи — `started` и отправка в `OrderedExecutor`; на каждом витке — `commitAsync(committable())`. Ограниченная очередь пока может блокировать раздачу — так и оставьте.

**Проверка — намеренная поломка.** Задержка проверки 1 секунда, поток 500 в секунду. Наблюдайте `max.poll.interval.ms`: блокирующая раздача остановит поток `poll()`, и экземпляр выбудет из группы — как в лабе 4.5. Запишите, через сколько секунд это произошло.

### Этап 4.4. Обратное давление

**Зачем.** Когда пул не успевает, поток `poll()` не должен ни блокироваться, ни раздавать без предела (М4, F.A.Q. и раздел 11).

**Что сделать.**

- два порога заполнения: верхний — `pause(assignment())`, нижний — `resume(paused())`. Почему два порога, а не один, — подумайте, что будет на границе с одним;
- раздача больше не блокирует: если на паузе — `poll()` вернёт пусто, и цикл продолжит вызывать его;
- записи, уже полученные в момент паузы, всё равно нужно раздать — решите, что делать, если очередь полна.

**Проверка.** Повторите поломку из этапа 4.3: экземпляр не выбывает, размер очереди не превышает предела, после возврата задержки к 100 мс лаг уменьшается. Это AC4.2.

### Этап 4.5. Ребалансировка

**Зачем.** У отзываемой партиции могут быть задачи в очереди и в работе. Их судьба — отдельное решение.

**Что сделать.** В `onPartitionsRevoked` есть два варианта:

- **дождаться** завершения задач отзываемых партиций, закоммитить готовый префикс и отдать партиции. Ожидание — часть бюджета `max.poll.interval.ms`;
- **бросить** их: убрать из очереди, закоммитить то, что готово сейчас. Брошенные задачи новый владелец выполнит повторно.

Выберите и обоснуйте. В обоих случаях после отзыва задачи этих партиций не должны ничего коммитить. В `onPartitionsLost` — только очистка, без коммита.

**Проверка.** AC4.3 и ребалансировка с добавлением второго экземпляра посреди потока.

### Критерии приёмки UC-4

| ID | Как воспроизвести | Ожидаемый результат | Доказательство |
|---|---|---|---|
| AC4.1 | 5 минут при 500 заказах/с, задержка 50–200 мс | лаг не растёт монотонно | замеры лага раз в 30 с |
| AC4.2 | задержка до 1 с на 2 минуты, затем обратно | очередь не больше предела; ни одного выбывания; лаг после восстановления падает | метрики + лог listener'а |
| AC4.3 | `kill -9` посреди потока, перезапуск | ни одного потерянного заказа; повторных проверок не больше, чем было в очереди и в работе | журнал проверок + сверка |
| AC4.4 | порядок по продавцу | для каждого продавца порядок проверок совпадает с порядком в партиции | журнал проверок + сверка с топиком |

Для AC4.3 и AC4.4 нужен журнал проверок: идентификатор заказа, продавец, партиция, оффсет, время. Пишите его так же, как журнал в UC-1, — не из потоков пула напрямую.

### Решения для README

- размеры пула и очередей — из расчёта;
- почему коммит максимального завершённого оффсета неверен;
- как сохранён порядок по продавцу и какова цена этого решения;
- почему два порога паузы;
- что происходит с задачами отзываемых партиций;
- когда эта модель **не нужна** и «потребитель на поток» лучше.

## UC-5. Наблюдение за отставанием

### Цель

Дежурному нужен инструмент, который по имени группы показывает отставание и поднимает тревогу. Лаг в записях не годится как общий порог: в кластере есть топики и с 500 записями в секунду, и с 5 (М4, раздел 13).

### Архитектура

| Класс | Отвечает за | API Kafka | Почему отдельно |
|---|---|---|---|
| `LagWatchApp` | параметры: группа, период, пороги; цикл замеров | — | — |
| `GroupState` | закоммиченные оффсеты группы и партиции, которые она сейчас читает | `Admin.listConsumerGroupOffsets`, `Admin.describeConsumerGroups` | что знает группа |
| `TopicState` | конец и начало каждой партиции | `Admin.listOffsets` с `OffsetSpec.latest()` и `OffsetSpec.earliest()` | что есть в топике |
| `LagCalculator` | лаг в записях и во времени по каждой партиции | — | чистая логика |
| `AlertRules` | правила T1–T4, хранит историю замеров для T2 | — | чистая логика, юнит-тесты |
| `Reporter` | вывод таблицы и сработавших правил | — | — |

### Правила тревоги

| Правило | Условие |
|---|---|
| T1 — отставание во времени | лаг во времени больше порога по любой партиции |
| T2 — рост | суммарный лаг растёт заданное число замеров подряд |
| T3 — угроза retention | закоммиченный оффсет ближе к log start offset, чем заданная доля размера партиции |
| T4 — нет коммита | у партиции, которую группа читает, нет закоммиченного оффсета |

### Этап 5.1. Состояние группы и топика

**Зачем.** Лаг — разность двух чисел из разных источников: что закоммитила группа и где конец партиции.

**Что сделать.**

- `Admin.create(props)` — без `group.id`: инструмент не входит в группу;
- закоммиченные оффсеты — `listConsumerGroupOffsets(group)`;
- какие партиции группа читает сейчас — назначения членов из `describeConsumerGroups`;
- конец и начало партиций — `listOffsets` с `OffsetSpec.latest()` и `OffsetSpec.earliest()`. `latest()` даёт high watermark, а не LEO (М2, F.A.Q.);
- вывести таблицу: партиция, закоммичено, конец, начало, лаг.

**Проверка.** Лаг по каждой партиции совпадает с `kafka-consumer-groups.sh --describe`.

**Типичные ошибки.** Партиция без коммита получает лаг 0 — та же ловушка, что в лабе 4.10. Партиция без коммита — это отдельное состояние, а не ноль.

### Этап 5.2. Лаг во времени

**Зачем.** Порог во времени одинаково осмыслен для топиков с разным потоком (М4, раздел 13).

**Что сделать.** Два способа — выберите один и обоснуйте:

- **через скорость записи** — по двум последовательным замерам конца партиции: скорость = прирост конца / время между замерами; лаг во времени = лаг / скорость. Не работает, пока в партицию не пишут, и неточен при неровном потоке;
- **через время записи на закоммиченном оффсете** — прочитать одну запись с этого оффсета и взять её время. Точнее, но нужен потребитель: `assign` + `seek` + `poll`, без `group.id`. Это не нарушает требование «не входить в группу».

**Проверка.** На медленном потребителе из лабы 4.10 лаг во времени растёт, и его порядок согласуется с `e2e-макс` зонда.

### Этап 5.3. Правила

**Зачем.** Таблица — для человека, правила — для тревоги.

**Что сделать.** `AlertRules` принимает замер и возвращает сработавшие правила. T2 требует истории замеров — храните последние K сумм. T3 — подумайте, что считать «размером партиции».

**Проверка.** Юнит-тесты на каждое правило: синтетические замеры, при которых правило срабатывает и не срабатывает.

### Критерии приёмки UC-5

| ID | Как воспроизвести | Ожидаемый результат | Доказательство |
|---|---|---|---|
| AC5.1 | медленный потребитель, как в лабе 4.10 | срабатывают T1 и T2; лаг совпадает с `kafka-consumer-groups.sh` по всем партициям | вывод инструмента и утилиты |
| AC5.2 | все потребители группы остановлены | лаг продолжает расти в выводе | вывод |
| AC5.3 | новая группа с `latest` и медленный потребитель, как в исходной лабе 4.10 | T4 по партициям без коммита | вывод |
| AC5.4 | топик с `retention.ms` в 2 минуты, остановленная группа | T3 срабатывает раньше, чем retention обгонит группу | вывод + `kafka-get-offsets.sh --time -2` |

### Решения для README

- способ подсчёта лага во времени, где он ошибается и почему этого достаточно;
- что считается «размером партиции» в T3;
- какие ситуации инструмент не ловит — например, прыжок `latest` из лабы 4.4 — и как их можно было бы обнаружить.
