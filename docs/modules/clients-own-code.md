## Как устроен блок

Пять use case на одном домене. Каждый разобран так:

- **цель** — что должно получиться и зачем это бизнесу;
- **архитектура** — какие классы нужны, за что отвечает каждый, какие API Kafka он использует и почему ответственность вынесена именно так;
- **поток данных** — как запись проходит через классы;
- **этапы** — порядок работы. У каждого этапа: зачем он, что сделать, какие API и настройки задействованы, как проверить, что этап готов, и какие ошибки здесь делают чаще всего;
- **критерии приёмки** — финальная проверка use case;
- **решения для README** — вопросы, ответ на которые вы записываете своими словами.

Код здесь не дан ни строчкой. Имена классов — предложение, а не требование: можно назвать иначе и разбить по-другому, если в README объяснено почему. Обязательно другое — разделение ответственности и поведение.

### Правила

1. Во время работы не открывайте `ProducerProbe`, `ConsumerProbe`, `ManualCommitConsumer`, `ProducerModes`, `TenantPartitioner`, `LagReporter`. Источники — теория модулей 3 и 4, Javadoc `KafkaProducer`, `KafkaConsumer`, `Admin` и документация конфигурации.
2. Зонды и утилиты Kafka можно использовать для проверки — как генератор нагрузки или измеритель, — но не как образец.
3. Этап считается готовым только после проверки из его описания. Не переходите к следующему, пока проверка не прошла: ошибки нижних этапов в верхних почти не диагностируются.
4. Логика без Kafka — расчёт префикса, правила тревоги, разбор события — покрывается юнит-тестами (JUnit и AssertJ уже есть в `labs/pom.xml`). Логика с Kafka проверяется сценариями.
5. **Окружение — одиночный брокер** из `compose.single.yml`, как в практике модулей 3 и 4. Все сценарии отказов воспроизводятся на нём: `docker pause` и `kill -9` из лаб. Ограничение одно: при RF=1 `acks=all` ничем не отличается от `acks=1`, поэтому гарантии репликации здесь не проверяются — решение по `acks` и `min.insync.replicas` записывается в README для продакшена с RF=3 (модуль 3, лаба 3.10 — там это проверялось на кластере).

## Общий контекст

Маркетплейс. Покупатели оформляют заказы, каждый заказ — событие `OrderEvent` из `common`: идентификатор заказа, продавец, сумма, тенант, время создания. События идут в топик `orders.created.v1`.

**Требование бизнеса к порядку:** события одного продавца обрабатываются в том порядке, в котором были приняты. От этого зависит баланс продавца, который пересчитывается по каждому заказу.

**Входные данные для расчётов:**

| Параметр | Значение |
|---|---|
| поток заказов | обычный 500 в секунду, пиковый 2000 |
| размер события | около 150 байт в JSON |
| продавцов | около 1000, распределение неравномерное |
| доля самого крупного продавца | до 5% всех заказов |
| обработка заказа в UC-2 | 2 мс в среднем, до 20 мс в пиковые периоды |
| антифрод-проверка в UC-4 | 50–200 мс, в среднем 100 |
| экземпляров обработчика UC-2 | до 8 |
| целевая загрузка потребителей | 60–70% (модуль 2, лаба 2.13) |

## Этап 0. Модуль и общие решения

### Зачем

Все пять use case живут в одном Maven-модуле и работают с одним топиком. Ключ записи и число партиций — решения, которые потом нельзя поменять без боли (модуль 2, разделы 2 и 9), поэтому они принимаются до первой строки кода.

### Что сделать

**Модуль.** Создайте `labs/own-clients` с собственным `pom.xml`:

- родитель — `labs`, как у `lab03-producer`;
- зависимость от `common` — оттуда `Env`, `OrderEvent`, `JsonSerde`; `kafka-clients` и логирование придут транзитивно;
- для UC-2 понадобится JDBC-драйвер встраиваемой базы — H2 (`com.h2database:h2`) или SQLite (`org.xerial:sqlite-jdbc`); добавите на этапе UC-2.

Добавьте модуль в `<modules>` в `labs/pom.xml`.

**Пакеты.** Предлагаемая раскладка:

| Пакет | Что там |
|---|---|
| `dev.learning.kafka.own.intake` | UC-1, приём заказов |
| `dev.learning.kafka.own.processing` | UC-2, обработка заказов |
| `dev.learning.kafka.own.replay` | UC-3, переигровка |
| `dev.learning.kafka.own.fraud` | UC-4, тяжёлая обработка |
| `dev.learning.kafka.own.lag` | UC-5, наблюдение за отставанием |

Общий код между use case не выносите заранее. Если что-то понадобится в двух местах — тогда и вынесете.

**Решения.** Запишите в `labs/own-clients/README.md`, раздел «Общие решения»:

- **ключ записи.** Требование бизнеса: события одного продавца обрабатываются по порядку. Что тогда ключ — `orderId` или `sellerId`? Учтите, что Javadoc `OrderEvent` в `common` предлагает `orderId` — объясните, почему ваше требование важнее;
- **число партиций.** Расчёт по методу лабы 2.13 — от узкого места, по входным данным из общего контекста:
  1. **Продюсер и брокер.** Пиковый поток в байтах в секунду — и сравните с тем, что одна партиция принимала в замерах модуля 3. Если запас огромный, число партиций определяется не записью;
  2. **Потребитель.** Одна партиция в группе читается одним членом последовательно (М4, раздел 2). Сколько заказов в секунду переработает один поток при 2 мс на заказ и при 20 мс? Сколько партиций нужно, чтобы выдержать пик с целевой загрузкой? Решите, по какому времени обработки считать, и обоснуйте;
  3. **Горячий ключ.** Все заказы одного продавца — в одной партиции. Выдержит ли одна партиция поток самого крупного продавца в пике? Добавление партиций эту проблему не решает (М2, лаба 2.3);
  4. **Число обработчиков.** Партиций не меньше, чем экземпляров в пике, иначе лишние простаивают (М4, лаба 4.3);
  5. **Делимость и рост.** Итоговое число округлите до хорошо делимого с учётом роста — партиции выбираются один раз (М4, F.A.Q. и раздел 2).

  UC-4 в расчёт не входит: там параллелизм внутри экземпляра, и число партиций его не ограничивает — это и проверяется в расчёте перед UC-4;
- **`acks` и `min.insync.replicas`.** Что на учебном одиночном брокере и что было бы в продакшене с RF=3 (М3, раздел 5).

Создайте топик:

```bash
$K $BIN/kafka-topics.sh --bootstrap-server $BS --create --topic orders.created.v1 \
  --partitions <ваше число> --replication-factor 1
```

```bash
cd labs
mvn -q -pl own-clients -am install -DskipTests
```

Собирается без ошибок, топик существует с выбранным числом партиций.

## UC-1. Приём заказов

### Цель

Сервис принимает заказы от витрины и публикует их в `orders.created.v1`. Витрину имитирует встроенный генератор. Главное требование: **принятый заказ не исчезает молча.** Для каждого заказа можно доказать его судьбу — подтверждён брокером или не отправлен, с причиной.

### Архитектура

| Класс | Отвечает за | API Kafka | Почему отдельно |
|---|---|---|---|
| `IntakeApp` | точка входа: собирает компоненты, задаёт порядок запуска и остановки | — | весь жизненный цикл виден в одном месте |
| `PropertiesHolder` | разбор аргументов на настройки продюсера и параметры сервиса, значения по умолчанию, проверка при старте | `ProducerConfig` — имена настроек | ошибка конфигурации обнаруживается при старте, а не при остановке |
| `OrderGenerator` | создаёт заказы с заданной скоростью в течение заданного времени и отдаёт их получателю | — | имитация витрины; замена на HTTP-контроллер не трогает публикацию |
| `OrderPublisher` | владеет единственным `KafkaProducer`: отправка, закрытие | `KafkaProducer`, `ProducerRecord`, `send(record, callback)`, `close(Duration)` | вся работа с продюсером — в одном месте; продюсер один на сервис (М3, раздел 12) |
| `PublishCallback` | реакция на результат отправки конкретного заказа | `Callback`, `RecordMetadata`, иерархия исключений | у каждого заказа своя судьба, и callback должен знать, чью судьбу фиксирует |
| `DeliveryJournal` | хранит судьбу заказов: принят, подтверждён, не отправлен с причиной | — | доказательство отсутствия тихих потерь; запись на диск не должна идти в Sender-потоке |
| `CountingInterceptor` | счётчики отправленных, подтверждённых и неудачных записей | `ProducerInterceptor` | наблюдение на уровне клиента, независимо от кода приложения |

### Что делает каждый класс

#### IntakeApp

Единственный класс, который знает обо всех остальных. Сам ничего не делает с заказами — только собирает, запускает и останавливает.

**Запуск, по порядку:**

1. `PropertiesHolder` разбирает аргументы. Если конфигурация неверна — сервис завершается здесь, ни один ресурс ещё не создан.
2. Создаётся журнал, затем публикатор: публикатору нужен журнал.
3. Создаётся генератор. Ему передаётся не `OrderPublisher` целиком, а только способ отдать заказ — функциональный интерфейс с одним методом, принимающим `OrderEvent`. Генератор не должен иметь возможности закрыть публикатор.
4. Регистрируется shutdown hook — **до** запуска генератора, иначе сигнал, пришедший в промежутке, обойдёт последовательность остановки.
5. Запускается поток генератора.

**Остановка — одна последовательность для обоих путей:**

```
основной поток:  ожидание завершения потока генератора   ← срок истёк или вызван stop()
                 publisher.close()                        ← буфер отправлен, все callback отработали
                 journal.close()                          ← очередь журнала дописана на диск

shutdown hook:   generator.stop()
                 ожидание завершения основного потока     ← иначе JVM завершится до close()
```

- Генератор остановился по сроку — основной поток проходит последовательность, JVM завершается, shutdown hook срабатывает, но делать ему уже нечего.
- Пришёл SIGTERM — shutdown hook останавливает генератор и ждёт; основной поток проходит ту же последовательность; shutdown hook дожидается её конца.

**Почему shutdown hook ждёт основной поток.** При остановке JVM ждёт завершения только shutdown hook, а не остальных потоков. Если shutdown hook вернётся сразу, JVM может завершиться посреди `publisher.close()`, и буфер пропадёт.

**Не делает:** не создаёт заказы, не отправляет записи, не обрабатывает результаты отправки.

#### PropertiesHolder

Превращает аргументы командной строки в две независимые конфигурации и гарантирует, что после его создания конфигурация корректна.

**Вход:** массив аргументов вида `ключ=значение`.

**Выход:**

- карта настроек продюсера — неизменяемая копия;
- параметры сервиса — уже **типизированные** значения, каждое через свой метод получения.

**Параметры сервиса:**

| Параметр | Тип | По умолчанию | Проверка |
|---|---|---|---|
| `wait.finish.ms` | миллисекунды | 5000 | больше нуля |
| `rate` | заказов в секунду | 500 | больше нуля |
| `duration` | длительность генерации | 1 минута | больше нуля, или особое значение «до остановки» — выберите какое и запишите |

Формат длительности выберите сами — секунды числом или ISO-8601 через `Duration.parse`, например `PT5M`. Запишите выбор в README.

**Правила:**

- аргумент разделяется по **первому** `=`; без `=`, с пустым ключом или пустым значением — `IllegalArgumentException` с текстом аргумента;
- параметр сервиса попадает только в параметры сервиса, всё остальное — только в настройки продюсера;
- значение параметра сервиса разбирается и проверяется **при создании**; ошибка называет параметр и значение;
- повтор ключа — побеждает последнее значение;
- после создания конфигурация не меняется: нет сеттеров, наружу отдаются копии;
- состояние принадлежит экземпляру, не классу.

**Не делает:** не создаёт продюсер и ничего не знает о том, как настройки будут использованы.

Поведение закреплено тестами `PropertiesHolderTest`. При добавлении параметров тесты дописываются.

#### OrderGenerator

Создаёт заказы равномерным потоком заданной скорости, пока не истечёт заданное время или пока его не остановят.

**Вход:** получатель заказов, скорость, длительность.

**Поток:** собственный. Запускает его `IntakeApp`; генератор реализует `Runnable` или владеет потоком сам — на ваш выбор.

**Цикл:**

1. При старте — момент начала по `System.nanoTime()` и срок окончания. Только монотонные часы: `System.currentTimeMillis()` может сдвинуть синхронизация времени.
2. Период между заказами — секунда, делённая на скорость.
3. Заказ номер i уходит в момент «начало + i × период». Генератор ждёт этого момента — `LockSupport.parkNanos` — и **после пробуждения** проверяет срок и флаг остановки, перед созданием заказа.
4. Создаёт заказ и отдаёт получателю.
5. Цикл заканчивается, когда наступил срок или выставлен флаг остановки.

**Цикл подробно.**

Цель цикла — чтобы заказ номер i ушёл в момент

```
tᵢ = начало + i × 1 000 000 000 / rate     (в наносекундах)
```

Момент считается от начала каждый раз заново, а не прибавлением периода к предыдущему моменту: так ошибки округления и задержки отдельных витков не накапливаются. Произведение i × 10⁹ помещается в `long` для любых разумных длительностей — переполнение наступит через сотни лет работы.

Переменные цикла: `начало` и `срок` — один раз при старте, по `System.nanoTime()`; `i` — номер следующего заказа.

Один виток:

1. **Вычислить момент** tᵢ.
2. **Проверить срок.** Если tᵢ не раньше срока — заказов в окне больше нет, выход. Так за длительность T уходит ровно `rate × T` заказов, без лишнего последнего.
3. **Дождаться момента.** Остаток = tᵢ − `nanoTime()`. Пока остаток больше нуля: `LockSupport.parkNanos(остаток)`, после возврата — проверить флаг остановки и прерывание, пересчитать остаток. Ожидание — именно цикл, а не один вызов: `parkNanos` может вернуться раньше времени (см. ниже).
4. **Проверить остановку** ещё раз — пока поток спал, могли вызвать `stop()`.
5. **Создать заказ и отдать получателю.**
6. **`i` на единицу больше**, к шагу 1.

Пример при `rate = 4`, период 250 мс:

| Заказ | Момент по расписанию | Что происходит |
|---|---|---|
| 0 | 0 мс | остаток 0 — отправка сразу |
| 1 | 250 мс | ожидание до 250 — отправка |
| 2 | 500 мс | ожидание до 500 — отправка, но `send()` висит 400 мс: буфер полон |
| 3 | 750 мс | цикл пришёл на шаг 3 в 900 мс: остаток отрицательный — отправка сразу |
| 4 | 1000 мс | ожидание 100 мс — расписание восстановлено |

**Отставание от расписания — решение.** В примере генератор нагнал расписание, отправив пропущенное подряд. Это модель «заказы продолжали приходить, пока сервис был занят»: после задержки получается всплеск. Альтернатива — пропускать прошедшие моменты, то есть «нагрузка, которую не успели принять, потеряна». Для проверки отказов (AC1.2–AC1.4) первая модель честнее: витрина не перестаёт присылать заказы оттого, что сервис занят. Выберите и запишите в README.

**Как работает `LockSupport.parkNanos(n)`.**

Останавливает **текущий поток** не дольше чем на `n` наносекунд. Поток переходит в состояние ожидания и не тратит процессор.

Возвращается в одном из четырёх случаев:

- истекло время;
- другой поток вызвал `LockSupport.unpark(этот поток)`;
- поток прервали — `interrupt()`;
- **без причины.** Документация прямо разрешает ложные пробуждения. Поэтому `parkNanos` всегда вызывают в цикле с проверкой условия, а не надеются на одно точное ожидание.

Метод не сообщает, почему вернулся, и не бросает `InterruptedException`. Отсюда главная ловушка: **флаг прерывания он не сбрасывает.** Если поток прервали, а цикл этого не проверил, каждый следующий `parkNanos` будет возвращаться мгновенно — генератор превратится в цикл, занимающий процессор на 100%. Поэтому после каждого возврата нужно проверять `Thread.currentThread().isInterrupted()` и выходить.

`unpark` работает через «разрешение»: если `unpark` вызван до `park`, следующий `park` вернётся сразу. Это ещё один источник внезапных возвратов, если в программе есть чужие вызовы `unpark`.

**Сравнение с другими способами ожидания:**

| Способ | Точность | Прерывание | Процессор |
|---|---|---|---|
| `Thread.sleep(ms)` | миллисекунды | бросает `InterruptedException` и сбрасывает флаг | не тратит |
| `LockSupport.parkNanos(ns)` | десятки микросекунд, зависит от ОС | не бросает, флаг не сбрасывает | не тратит |
| пустой цикл до момента | наносекунды | только своя проверка | 100% ядра |

**Точность и скорость.** В Linux минимальное реальное ожидание `parkNanos` — порядка десятков микросекунд: столько стоит переход потока в ожидание и обратно. При 2000 заказах в секунду период — 500 мкс, и этой точности достаточно. При десятках тысяч в секунду период становится сравним с накладными расходами, и генератор начнёт отставать — тогда за одно пробуждение отправляют несколько заказов, чьи моменты уже наступили. В этом блоке такие скорости не нужны, но если увидите, что фактическая скорость ниже заданной, — причина здесь.

**Досрочное пробуждение при остановке.** При 500 заказах в секунду поток спит 2 мс, и флаг остановки он увидит почти сразу. Будить его нужно, только если период большой — например, при `rate = 1` поток спит секунду. Тогда `stop()` после выставления флага может вызвать `LockSupport.unpark(поток генератора)` или `interrupt()`.

**Почему расписание от начала, а не пауза после каждого заказа.** При паузе время самой отправки добавляется к периоду, и скорость плывёт вниз. При расписании от начала отставание одного витка нагоняется следующими.

**Почему не пачка раз в секунду.** `rate` заказов, отправленных подряд раз в секунду, дают ту же среднюю скорость, но для продюсера это пачка за миллисекунды и почти секунда тишины. Батчинг, задержка и все замеры в критериях приёмки будут про пачки, а не про поток.

**Заказ:**

| Поле | Как заполняется | Почему |
|---|---|---|
| `orderId` | глобально уникальный, например UUID | номер от нуля повторяется между запусками: ломает сверку журнала с топиком и дедупликацию в UC-2 |
| `sellerId` | ~1000 продавцов, самый крупный — около 5% заказов | неравномерность из общего контекста; способ выбора — в README |
| `amount` | сумма заказа | понадобится в UC-2 для сверки балансов |
| `tenant` | значение тенанта | поле контракта `OrderEvent` |
| `createdAt` | момент создания заказа | бизнес-время заказа; см. решение о таймстемпе записи в `OrderPublisher` |

Случайные числа — `ThreadLocalRandom`, без фиксированного зерна: последовательности не должны повторяться между запусками.

**Остановка:** метод `stop()` только выставляет флаг. Флаг — `volatile` или `AtomicBoolean`: обычное поле, изменённое в shutdown hook, поток генератора может не увидеть. Если генератор спит до следующего заказа, разбудить его досрочно можно через `interrupt()`; флаг прерывания при этом восстанавливается, а не проглатывается.

**Ошибка при отправке одного заказа** не должна молча останавливать поток. Решите и запишите, что правильнее: зафиксировать и продолжить или остановить сервис явно, с сообщением. Учтите, что `send()` может бросить исключение синхронно — например, после закрытия продюсера, — и что этот заказ уже числится в журнале принятым.

**Не делает:** не знает о Kafka, не закрывает получателя, не управляет порядком остановки.

**Проверка без Kafka:** подставьте вместо публикатора счётчик — за 10 секунд при 500 в секунду он должен получить около 5000 заказов, равномерно по секундам.

#### OrderPublisher

Владеет продюсером и превращает заказ в запись Kafka.

**Вход:** настройки продюсера, таймаут закрытия, журнал.

**`accept(order)`:**

1. Отметить заказ в журнале как принятый — **до** `send()`, чтобы падение после `send()` не стёрло заказ из журнала.
2. Построить `ProducerRecord`: топик, ключ по общему решению, значение — заказ. Таймстемп записи — решение: оставить время `send()` или передать `createdAt` явно через конструктор `ProducerRecord` с таймстемпом. От этого зависит, по какому времени UC-3 будет искать заказы.
3. Вызвать `send(record, callback)`, где callback — **новый для каждого заказа** и знает его `orderId`. Общий экземпляр на все записи не знает, чью судьбу фиксировать.
4. Если `send()` бросил исключение синхронно — зафиксировать заказ в журнале как не отправленный с причиной. `send()` бросает синхронно только ошибки, которые клиент не считает ошибками Kafka; ошибки Kafka, включая таймаут `max.block.ms`, приходят в callback (М3, раздел 9).

**Потоки:** `accept` вызывается из потока генератора, callback — в Sender-потоке, а при ошибках внутри `send()` — в потоке генератора. Всё, что разделяют эти потоки, должно быть потокобезопасным.

**`close()`:** `producer.close(Duration)` с таймаутом из параметров. Записи, не отправленные за таймаут, клиент завершит с ошибкой, и их callback сработают — журнал зафиксирует их как неотправленные.

**Не делает:** не создаёт заказы, не пишет на диск, не решает, когда остановиться.

#### PublishCallback

Фиксирует судьбу одного заказа. Реализует `org.apache.kafka.clients.producer.Callback`; `onCompletion` — с `@Override`.

**Вход:** `orderId` заказа и журнал — через конструктор.

**`onCompletion(metadata, exception)`:**

- без исключения — заказ подтверждён: журнал получает `orderId`, партицию и оффсет;
- с исключением — заказ не отправлен: журнал получает `orderId` и причину, где различимы два класса ошибок из этапа 1.4.

**Ограничения:** выполняется в Sender-потоке — никакой медленной работы, только передача в журнал. Никогда не вызывает `send()`: повтор — это новая запись с новым номером последовательности.

#### DeliveryJournal

Доказательство того, что ни один заказ не исчез молча. Инвариант, который журнал должен позволять проверить после остановки сервиса:

> каждый принятый заказ имеет ровно одну судьбу — подтверждён или не отправлен.

**Операции:**

| Операция | Кто вызывает | В каком потоке |
|---|---|---|
| `accepted(orderId)` | `OrderPublisher.accept`, до `send()` | поток генератора |
| `acked(orderId, partition, offset)` | `PublishCallback` | Sender-поток |
| `failed(orderId, причина)` | `PublishCallback` | Sender-поток, а при отказе внутри `send()` — поток генератора |
| `failed(orderId, причина)` | `OrderPublisher.accept`, если `send()` бросил исключение | поток генератора |
| `close()` | `IntakeApp`, последним | основной поток |

Писать в журнал будут как минимум два потока одновременно, а на диск — только один. Это классическая схема «много производителей — один потребитель».

**Устройство: очередь и поток записи.**

```
поток генератора ──┐
                   ├──▶ очередь событий ──▶ поток журнала ──▶ accepted.log
Sender-поток ──────┘                                     ├──▶ acked.log
                                                         └──▶ failed.log
```

Операции журнала только кладут событие в очередь и сразу возвращают управление. Поток журнала забирает события и пишет их в файлы. Так запись на диск никогда не выполняется в Sender-потоке: медленный диск не тормозит отправку всех партиций (М3, лаба 3.9).

Подходящая структура — `BlockingQueue`. Поток журнала эффективнее забирает события не по одному, а пачкой: одно блокирующее ожидание первого события, затем `drainTo` всего, что накопилось, и одна запись пачки в файлы.

**Что делать, когда очередь полна — главное решение класса.** Если диск остановился на несколько секунд, очередь растёт со скоростью до трёх событий на заказ. Три варианта поведения:

| Вариант | Что происходит | Опасность |
|---|---|---|
| неограниченная очередь | память растёт без предела | при долгом сбое диска — нехватка памяти, и сервис падает целиком |
| ограниченная, ждать места (`put`) | вызывающий поток блокируется | если ждёт **Sender-поток** — встаёт отправка всех записей продюсера |
| ограниченная, не ждать (`offer`) и считать переполнения | событие теряется, счётчик растёт | журнал перестаёт быть доказательством — но вы об этом знаете |

Варианты можно сочетать по потокам. Блокировать поток генератора допустимо — это естественное обратное давление на приём, как `max.block.ms` у продюсера. Блокировать Sender-поток нельзя. Выберите поведение для каждого потока и обоснуйте в README. Ёмкость очереди посчитайте: скорость в пике × события на заказ × сколько секунд задержки диска вы готовы пережить. Например, 2000 × 3 × 10 = 60 000 событий.

**Формат файлов:**

| Файл | Строка | Зачем |
|---|---|---|
| `accepted.log` | `orderId` | множество принятых |
| `acked.log` | `orderId` партиция оффсет | множество подтверждённых и место в топике |
| `failed.log` | `orderId` класс-ошибки сообщение | множество неотправленных и причина; класс — один из трёх из этапа 1.4 |

Одна строка — одно событие, разделитель — пробел или табуляция. Сообщение исключения может содержать переводы строк — заменяйте их, иначе строка развалится, и сверка через `sort` и `comm` сломается. Первым полем всегда `orderId`: тогда `cut -f1` даёт множество идентификаторов из любого файла.

**Куда писать.** Каталог журнала — параметр сервиса в `PropertiesHolder`. Решите, что делать с файлами прошлого запуска: дописывать, перезаписывать или создавать каталог на каждый запуск. При дописывании сверка «принятые без подтверждения» смешает запуски — даже при уникальных `orderId` старые неотправленные заказы будут мешать считать новые.

**Когда сбрасывать на диск.** `BufferedWriter` копит строки в памяти. Если процесс убит `kill -9`, несброшенное пропадает, и журнал покажет меньше, чем было на самом деле. Достаточно вызывать `flush()` после каждой записанной пачки: после `flush()` данные лежат в кеше операционной системы и переживают смерть процесса — это тот же page cache, что у брокера Kafka (модуль 1). `fsync` нужен только против падения самой ОС или отключения питания, в этом блоке он не требуется.

**Порядок событий.** `accepted` попадает в очередь до вызова `send()`, а `acked` и `failed` — после. Поэтому в одной очереди событие о принятии заказа всегда раньше события о его судьбе. Это и позволяет проверять инвариант простыми множествами.

**Закрытие.**

1. `close()` вызывается после `publisher.close()` — к этому моменту все callback отработали, новых событий не будет.
2. Поток журнала должен узнать, что пора заканчивать, **дописать всё, что осталось в очереди**, и завершиться. Сигналом может быть особое событие-маркер в очереди или флаг плюс опустошение очереди — выберите сами.
3. `close()` дожидается завершения потока журнала и закрывает файлы.

Событие, пришедшее после закрытия, — признак нарушенного порядка остановки. Не теряйте его молча: считайте и выводите.

**Метрики журнала:** текущий размер очереди, записано событий, переполнений. Выводите их вместе со счётчиками сервиса.

**Проверка инварианта после остановки:**

```bash
cut -f1 accepted.log | sort -u > /tmp/a
cut -f1 acked.log    | sort -u > /tmp/k
cut -f1 failed.log   | sort -u > /tmp/f
comm -23 /tmp/a <(sort -u /tmp/k /tmp/f) | wc -l     # принятые без судьбы — должно быть 0
comm -12 /tmp/k /tmp/f | wc -l                       # и подтверждён, и не отправлен — должно быть 0
```

Команды написаны для табуляции; для другого разделителя укажите его в `cut -d`, например `cut -d: -f1`.

**Не делает:** не решает, что делать с неотправленными заказами, и не повторяет их.

#### CountingInterceptor

Учёт записей на уровне клиента Kafka, независимый от вашего кода. Если приложение где-то потеряет ошибку — в callback, в журнале, — интерсептор её всё равно увидит. Расхождение его счётчиков с журналом и есть сигнал такой потери.

**Интерфейс.** Класс реализует `org.apache.kafka.clients.producer.ProducerInterceptor<String, OrderEvent>` — типы те же, что у продюсера. Клиент проверяет это при создании продюсера: класс из `interceptor.classes`, не реализующий интерфейс, не позволит продюсеру создаться. Методы интерфейса — `configure(Map<String, ?>)`, `onSend`, `onAcknowledgement`, `close` — помечайте `@Override`: опечатка в имени метода без этой аннотации даёт просто новый метод, который клиент никогда не вызовет, и компилятор промолчит.

**Жизненный цикл.** Экземпляр создаёт `KafkaProducer` — через рефлексию, поэтому классу нужен публичный конструктор без аргументов. Подключается настройкой `interceptor.classes` с полным именем класса. Дальше клиент вызывает методы сам:

| Метод | Когда | В каком потоке |
|---|---|---|
| `configure(Map)` | один раз при создании продюсера | основной поток |
| `onSend(record)` | в начале каждого `send()`, до сериализации и выбора партиции | поток, вызвавший `send()` |
| `onAcknowledgement(metadata, exception)` | когда судьба записи известна: подтверждена или ошибка | Sender-поток; при ошибке внутри `send()` — поток, вызвавший `send()` |
| `close()` | при закрытии продюсера | поток, вызвавший `close()` |

Обратите внимание на последнюю строку `onAcknowledgement`: клиент вызывает его и для ошибок, случившихся ещё внутри `send()`, — например, при отказе по `max.block.ms` или ошибке сериализации. Поэтому счётчик ошибок интерсептора включает и отказы в приёме, и ошибки доставки.

**Счётчики:**

| Счётчик | Где растёт |
|---|---|
| отправлено | `onSend` |
| подтверждено | `onAcknowledgement` без исключения |
| ошибок | `onAcknowledgement` с исключением |

Методы вызываются из разных потоков, поэтому счётчики — `LongAdder` или `AtomicLong`. В любой момент `отправлено − подтверждено − ошибок` — это записи в полёте. После закрытия продюсера должно выполняться `отправлено = подтверждено + ошибок`: если нет, какая-то запись не получила судьбы.

**`onSend` должен вернуть запись** — ту же или изменённую, ведь интерсепторы могут менять записи. Возврат `null` сломает отправку.

**Исключение внутри интерсептора** клиент перехватывает и пишет в лог, а запись отправляется дальше. Ошибка в вашем интерсепторе не остановит продюсер — но молча испортит счётчики. Это ещё одна причина сверять их с журналом.

**Как вывести счётчики, если экземпляр создаёт клиент.** Ссылки на интерсептор у вашего кода нет. Варианты:

| Вариант | Плюсы | Минусы |
|---|---|---|
| интерсептор сам печатает счётчики по таймеру: таймер запускается в `configure()`, останавливается в `close()` | интерсептор самодостаточен | ещё один поток; вывод не синхронизирован с выводом сервиса |
| статические счётчики класса | проще всего читать из `IntakeApp` | глобальное состояние: два продюсера в одном процессе или тесты смешают счётчики |
| реестр, в котором интерсептор регистрируется в `configure()` | счётчики доступны сервису, состояние у экземпляра | нужен способ сообщить интерсептору, куда регистрироваться |

**Период вывода — настройка самого интерсептора.** Её можно передать через настройки продюсера: клиент отдаёт в `configure()` все переданные ему настройки, включая неизвестные (М3, раздел 11). Вспомните лабу 3.11: если интерсептор прочитает настройку в `configure()`, клиент не будет предупреждать о ней как о неиспользованной, а опечатку в её имени молча заменит значение по умолчанию. Проверьте значение в `configure()` и при ошибке бросьте исключение — продюсер тогда не создастся, и это правильно.

**Проверка:**

1. минута при 500 заказах в секунду — после закрытия `отправлено = подтверждено + ошибок`, и числа совпадают с журналом;
2. заказ с огромным полем `tenant` (этап 1.4) — счётчик ошибок интерсептора и журнал неотправленных выросли на один;
3. отказ по `max.block.ms` (этап 1.6) — тоже виден в счётчике ошибок интерсептора.

**Не делает:** ничего не пишет на диск, не меняет записи, не принимает решений о повторе.

### Этап 1.1. Конфигурация и публикатор

**Зачем.** Гарантии продюсера зависят от нескольких настроек сразу, и часть из них молча меняет другие (М3, лаба 3.5). Первым делом — конфигурация, которую нельзя ослабить случайно, и которая ломается при старте, а не при остановке.

**Что сделать.** `PropertiesHolder` по описанию выше, пока с одним параметром сервиса — `wait.finish.ms`. `OrderPublisher` создаёт и закрывает продюсер. Настройки продюсера задаются явно, даже если совпадают с умолчанием:

| Настройка | Почему явно |
|---|---|
| `enable.idempotence=true` | явное значение превращает противоречие в ошибку старта (М3, раздел 8) |
| `acks=all` | гарантия записи (М3, раздел 5) |
| `delivery.timeout.ms` | предел жизни записи в продюсере (М3, раздел 6) |
| `max.block.ms` | предел ожидания внутри `send()` (М3, раздел 2) |
| `linger.ms`, `batch.size` | под нагрузку 500–2000 в секунду, по замерам модуля 3 |

**Проверка:**

1. без параметров — старт и закрытие; в логе `ProducerConfig values` ваши значения (`acks = -1`, `enable.idempotence = true`);
2. `acks=1` — `ConfigException` при создании продюсера (AC1.5);
3. `wait.finish.ms=abc` и `wait.finish.ms=-1` — ошибка при старте с именем параметра;
4. аргумент без `=` — ошибка с текстом аргумента;
5. `mvn -q -pl own-clients -am test` — тесты `PropertiesHolderTest` зелёные.

**Типичные ошибки.** Значение параметра сервиса проверяется при использовании, а не при разборе; состояние в статических полях; продюсер создаётся до того, как проверено всё, что может упасть.

### Этап 1.2. Генератор и отправка

**Зачем.** Минимальный рабочий поток: заказы равномерно уходят в топик, а сервис останавливается сам по истечении времени.

**Что сделать.**

- параметры `rate` и `duration` в `PropertiesHolder`, с проверкой при старте;
- `OrderGenerator` по описанию выше;
- `OrderPublisher.accept` с callback на каждый заказ — пока callback только считает успехи и ошибки;
- в `IntakeApp` — запуск и последовательность остановки по описанию выше, пока без журнала.

**Проверка.** Подробная процедура — ниже, в разделе «Как проверять этапы 1.2 и 1.3».

**Типичные ошибки.** `send().get()` в генераторе (М3, лаба 3.1); пачка раз в секунду вместо равномерного потока; задача в `ScheduledExecutorService`, которая молча отменяется после первого исключения; shutdown hook, который не ждёт основной поток.

### Этап 1.3. Журнал судьбы заказов

**Зачем.** Требование «ни один заказ не исчезает молча» нужно уметь доказать.

**Что сделать.** `DeliveryJournal` по описанию выше — включая решение о поведении при полной очереди и каталог журнала как параметр сервиса; `OrderPublisher` отмечает принятые, `PublishCallback` — подтверждённые и неотправленные; `IntakeApp` закрывает журнал последним.

**Проверка.** Подробная процедура — ниже, в разделе «Как проверять этапы 1.2 и 1.3».

**Типичные ошибки.** Запись в файл прямо в callback; `accepted` после `send()`; Sender-поток блокируется на полной очереди; поток журнала не дописывает очередь при закрытии; переводы строк в сообщениях исключений.

**Что проверяем.** Последовательность остановки: генератор прекращает создавать заказы, публикатор отправляет буфер, журнал дописывает очередь, процесс выходит штатно.

#### 1.3-Д. Журнал после kill -9

**Что проверяем.** Сколько теряет журнал, когда процесс убит без shutdown hook, и согласуется ли это с выбранной политикой сброса на диск.

**Ожидается.** Нули больше не обязательны — это проверка масштаба потерь, а не их отсутствия:

**Что записать.** Оба числа и объяснение через политику сброса: как часто поток журнала вызывает `flush()`, и почему после `flush()` данные переживают `kill -9`, а без него — нет. Если числа в тысячи — журнал сбрасывает реже, чем вы думаете, или очередь журнала копит события.


### Этап 1.4. Классификация ошибок

**Зачем.** Когда callback получил исключение, клиент уже исчерпал свои ретраи (М3, раздел 6). Ваш код не повторяет — он фиксирует, **что известно о судьбе заказа** и **что с ним можно делать дальше**. Эти два вопроса и задают классы ошибок.

**Три класса:**

| Класс | Примеры | Записан ли заказ | Переотправка | Что сигнализирует |
|---|---|---|---|---|
| **отказ в приёме** | `BufferExhaustedException`, `TimeoutException` по метаданным — ожидание дольше `max.block.ms` | точно нет: запись не попала даже в буфер | безопасна, дубля не будет | сервис не успевает или брокер недоступен уже долго — вопрос мощности |
| **результат неизвестен** | `TimeoutException` по `delivery.timeout.ms` — «Expiring N record(s)» | неизвестно: брокер мог записать, но не ответить (М3, лаба 3.8) | возможна, но может дать дубль — нужна дедупликация у потребителя | недоступность брокера или сети |
| **окончательная** | `RecordTooLargeException`, `SerializationException`, ошибки авторизации, несуществующий топик | точно нет | бессмысленна: повтор упадёт так же | ошибка в данных или конфигурации — нужен человек |

**Почему именно так.** Класс ошибки определяет, что делать с заказом потом. Отказы в приёме можно переотправить автоматически. Неизвестные — только при дедупликации на стороне потребителя, иначе на балансе появится двойная сумма. Окончательные — разобрать и исправить. Если все ошибки записаны одной строкой «не отправлен», это решение уже не принять.

**Как различить первые два класса.** Оба — `TimeoutException` (`BufferExhaustedException` его подкласс), а разбор текста сообщения хрупок. Надёжнее признак **момента**: отказ в приёме происходит **внутри** `send()`, и callback вызывается в потоке генератора до того, как `send()` вернул управление. Ошибка доставки приходит позже, в Sender-потоке. Так как callback создаётся на каждый заказ, публикатор может отметить в нём, что `send()` уже вернулся, — и callback по этой отметке поймёт, какой случай перед ним. Продумайте, как сделать отметку видимой между потоками.

Базовый класс ретраибельных ошибок — `RetriableException`. При бесконечном `retries` ретраибельная ошибка доставки в итоге всегда приходит как истечение `delivery.timeout.ms`, поэтому «ретраибельная» в callback на практике означает «результат неизвестен», если это не отказ в приёме.

**Что сделать.** `PublishCallback` относит каждую ошибку к одному из трёх классов. Класс — отдельное поле в журнале неотправленных, а не часть текста сообщения: по нему потом фильтруют. Счётчики сервиса — по классам.

**Проверка.**

- заказ, сериализованный размер которого больше `max.request.size`, — например, с огромной строкой в поле `tenant`, — в журнале с классом «окончательная», без повторов;
- отказ в приёме — на этапе 1.6;
- результат неизвестен — AC1.3: только записи этого класса могут оказаться в топике.

**Типичные ошибки.** Повтор `send()` из callback; класс ошибки определяется по тексту сообщения; отказ в приёме и истечение доставки записаны одинаково.

### Этап 1.5. Интерсептор

**Зачем.** Счётчики на уровне клиента, которые не зависят от вашего кода.

**Что сделать.** `CountingInterceptor` по описанию выше.

**Проверка.** Три проверки из описания `CountingInterceptor`.

**Типичные ошибки.** Счётчики без синхронизации; `onSend` возвращает `null`; нет публичного конструктора без аргументов; статические счётчики, которые смешивают два продюсера.

### Этап 1.6. Заполненный буфер

**Зачем.** При недоступном брокере буфер заполняется, и `send()` начинает блокировать поток генератора — в реальном сервисе это поток обработки HTTP-запроса (М3, раздел 2).

**Что сделать.**

- выберите `max.block.ms` — сколько витрина готова ждать ответа. Это же время, на которое может задержаться остановка генератора: пока поток висит в `send()`, он не проверяет флаг;
- ошибки ожидания по `max.block.ms` приходят не исключением из `send()`, а в callback, вызванный **в потоке генератора внутри `send()`** (М3, лаба 3.7). Это отказ в приёме, а не ошибка доставки — callback должен их различать;
- отказы в приёме считаются отдельно и выводятся.

**Проверка.** AC1.4.

### Этап 1.7. Штатная остановка под нагрузкой

**Зачем.** Последовательность остановки описана в `IntakeApp`. Здесь она проверяется в худшем случае: остановка посреди потока при заполненном буфере.

**Что сделать.** Убедитесь, что последовательность соблюдена и что записи, не отправленные за `wait.finish.ms`, получают в журнале судьбу «не отправлен». Подумайте, что произойдёт, если поменять местами закрытие публикатора и журнала, и запишите.

**Проверка.** AC1.6, затем то же с паузой брокера во время остановки.

## UC-2. Обработка заказов

### Цель

Обработчик читает `orders.created.v1` и по каждому заказу прибавляет сумму к балансу продавца. Повторная обработка удвоит сумму — поэтому **баланс должен быть верным при любых сбоях и ребалансировках.** Доставка — at-least-once, результат — effectively-once (М4, раздел 5).

Ради этого UC-2 и устроен: Kafka гарантирует, что каждый заказ придёт хотя бы раз, а хранилище гарантирует, что учтён он будет ровно один раз. Ни одна из сторон в одиночку этого не обеспечивает.

### Архитектура

| Класс | Отвечает за | API | Почему отдельно |
|---|---|---|---|
| `ProcessorApp` | точка входа: порядок запуска и остановки, shutdown hook с `wakeup()` | `KafkaConsumer.wakeup()` | жизненный цикл в одном месте, как в UC-1 |
| `ProcessorConfig` | разбор аргументов на настройки потребителя и параметры сервиса, проверка при старте | `ConsumerConfig` | ошибка конфигурации — при старте |
| `ProcessingLoop` | цикл `poll()`: разбор, применение, учёт оффсетов, коммит, закрытие потребителя | `subscribe`, `poll`, `commitAsync`, `commitSync`, `close` | **весь** доступ к потребителю — в одном потоке и одном классе |
| `OrderParser` | значение записи → `OrderEvent` или «битая запись» | — | битая запись не должна ронять `poll()` |
| `BalanceStore` | балансы и отметки обработанных заказов, атомарно | JDBC | идемпотентность обеспечивает хранилище, а не память процесса |
| `OffsetTracker` | для назначенных партиций — оффсет следующей записи после обработанной | `TopicPartition`, `OffsetAndMetadata` | что коммитить — знание, нужное и циклу, и listener'у |
| `RebalanceHandler` | реакция на отзыв, назначение и потерю партиций | `ConsumerRebalanceListener` | у каждого метода свой контракт (М4, раздел 9) |
| `PoisonLog` | битые записи: партиция, оффсет, сырое значение | — | битая запись не теряется без следа |

### Что делает каждый класс

#### ProcessorApp

Собирает компоненты, запускает цикл в **основном потоке** и гарантирует закрытие всего, что открыто.

**Почему цикл в основном потоке.** `KafkaConsumer` не потокобезопасен (М4, раздел 1): создаётся, используется и закрывается он в одном потоке. Отдельный поток для цикла ничего не даёт — основной поток всё равно только ждал бы его. В UC-1 генератор работал в своём потоке, потому что основной поток был нужен для порядка остановки; здесь порядок остановки — это конец самого цикла.

**Запуск, по порядку:**

1. `ProcessorConfig` разбирает аргументы. Ошибка — завершение здесь, ничего не создано.
2. Открывается `BalanceStore`: соединение с базой, создание таблиц, если их нет. Хранилище недоступно — завершение до создания потребителя.
3. Открывается `PoisonLog`.
4. Создаётся `ProcessingLoop` — внутри него создаётся потребитель.
5. Регистрируется shutdown hook: `wakeup()` потребителя и ожидание завершения основного потока.
6. Основной поток выполняет цикл.

**Остановка:**

```
shutdown hook:    loop.wakeup()                   ← единственный потокобезопасный метод потребителя
                  ожидание основного потока

основной поток:   poll() или коммит бросает WakeupException → выход из цикла
                  финальный commitSync, consumer.close()   ← внутри ProcessingLoop, в finally
                  poisonLog.close(), store.close()        ← в finally ProcessorApp
```

Закрытие — **в `finally`**, при любом выходе из цикла: штатном, по сигналу или по ошибке. Урок UC-1: исключение, брошенное до закрытия, оставляет живые потоки, и процесс не завершается.

**Код выхода.** Ошибка обработки должна давать ненулевой код. Исключение, вышедшее из `main` после закрытия ресурсов, это и обеспечивает. Не вызывайте `System.exit` из основного потока — shutdown hook ждёт основной поток, а `System.exit` ждёт shutdown hook (UC-1).

**Не делает:** не обрабатывает записи и не знает, что такое оффсет.

Тот же принцип, что `PropertiesHolder` в UC-1. Две программы теперь разбирают аргументы одинаково — это повод вынести общий разбор в один класс, а различия оставить в двух конфигурациях. Решите сами и запишите в README.

**Не делает:** не создаёт потребитель и не открывает базу.

#### ProcessingLoop

Единственный класс, который трогает `KafkaConsumer`.

**Конструктор:** создаёт потребитель с настройками из конфигурации, `OffsetTracker` и `RebalanceHandler`, и подписывается на топик: `subscribe(список топиков, handler)`.

**Цикл:**

1. `poll(Duration)` — таймаут ожидания порядка сотен миллисекунд. Он определяет, как быстро цикл заметит, что пора вывести счётчики, но не влияет на скорость обработки: при потоке данных `poll` возвращается сразу.
2. Для каждой записи пачки, по порядку:
   - `OrderParser` разбирает значение;
   - битая запись — в `PoisonLog`, счётчик битых;
   - разобранная — `BalanceStore.apply`; результат «применён» или «повтор» — в счётчики;
   - в любом из трёх случаев — `tracker.done(партиция записи, оффсет + 1)`.
3. После пачки — `commitAsync(tracker.snapshot(), callback)`. Callback ошибки коммита только считает и пишет в лог: пропущенный коммит перекроется следующим (М4, раздел 3).
4. Раз в период — вывод счётчиков. Из этого же потока: так счётчикам не нужна синхронизация, а `consumer.metrics()` вызывается из потока, которому принадлежит потребитель.

**Почему `done` и для битой записи.** Иначе её оффсет никогда не будет закоммичен, и после каждого перезапуска обработчик будет спотыкаться о неё снова.

**Почему коммит после пачки, а не после каждой записи.** Коммит — запрос к координатору. Коммит на каждую запись при 500 заказах в секунду — 500 запросов в секунду ради экономии нескольких повторов при сбое. Повторы безвредны благодаря `BalanceStore`; число запросов — нет.

**Выход из цикла:**

- `WakeupException` — штатная остановка, не ошибка;
- исключение `BalanceStore` — например, база недоступна. Ретраить здесь бесконечно опасно: цикл перестанет вызывать `poll()`, и сработает `max.poll.interval.ms`. Правильнее остановиться **без коммита** обработанного после последнего успешного применения и выйти с ошибкой: при перезапуске записи придут снова, а `BalanceStore` отсеет то, что уже применено.

**`finally`:**

1. `commitSync(tracker.snapshot())` — но только если выход штатный. При выходе по ошибке хранилища коммитить нельзя: трекер может содержать оффсеты записей, применение которых не подтверждено.
2. `consumer.close(Duration)` — выход из группы. Внутри `close()` вызовет `onPartitionsRevoked` для всех партиций (М4, раздел 9).

**Не делает:** не знает, как устроена база, и не форматирует строки файлов.

#### OrderParser

Превращает строку значения в заказ или сообщает, что запись битая. Без исключений наружу.

**Почему не десериализатор Kafka.** Если `JsonSerde.deserializer()` подключить как `value.deserializer`, ошибку разбора бросит **`poll()`**, а позиция потребителя на битой записи не сдвинется. Каждый следующий `poll()` будет бросать ту же ошибку — обработчик застрянет навсегда. Разбор в своём коде даёт контроль: битая запись фиксируется, и цикл идёт дальше.

**Результат** — тип с двумя вариантами: «разобрано» с `OrderEvent` и «битая» с причиной. Подойдёт `sealed`-интерфейс, как `JournalEvent` в UC-1.

**Что считается битой записью** — решение. Минимум: не JSON, нет `orderId` или `sellerId`, значение `null`. Подумайте, считать ли битой запись с отрицательной суммой: это ошибка данных, которая пройдёт разбор, но испортит баланс.

**Проверка без Kafka** — юнит-тесты: корректный JSON, мусор, пустая строка, JSON без обязательных полей.

#### BalanceStore

Сердце UC-2. Делает повторную обработку безвредной.

**Схема — две таблицы:**

| Таблица | Поля | Ключ |
|---|---|---|
| балансы | продавец, сумма | продавец |
| обработанные заказы | идентификатор заказа, продавец, сумма, время обработки | идентификатор заказа |

**`apply(order)` — в одной транзакции:**

1. Вставить заказ в таблицу обработанных.
2. Если вставка нарушила первичный ключ — заказ уже обработан: откатить транзакцию, вернуть «повтор».
3. Иначе — прибавить сумму к балансу продавца (вставить строку баланса, если её нет), зафиксировать транзакцию, вернуть «применён».

**Почему вставка, а не проверка «уже есть?» перед ней.** Во время ребалансировки старый и новый владелец партиции могут на короткое время обрабатывать одну запись одновременно. Оба выполнят проверку, оба увидят «нет», оба прибавят сумму. Первичный ключ решает это на уровне базы: вторая вставка гарантированно упадёт. Нарушение уникальности опознаётся по коду SQLState `23505` — его возвращают и H2, и PostgreSQL.

**Почему одна транзакция.** Если отметка и баланс фиксируются раздельно, сбой между ними даёт либо потерянную сумму — отметка есть, баланса нет, и повтор её отбросит, — либо двойную.

**Общее хранилище для нескольких экземпляров.** В AC2.1 работают два экземпляра обработчика. Если у каждого своя база, балансы разойдутся: при ребалансировке партиция переедет к другому экземпляру, и его база не знает, какие заказы уже обработаны первым. Хранилище должно быть **одно на всех**:

- **H2 в смешанном режиме** — строка подключения с `;AUTO_SERVER=TRUE`: первый процесс открывает файл базы и поднимает сервер, следующие подключаются к нему по сети;
- **PostgreSQL в контейнере** рядом с брокером — ближе к реальности, но ещё один сервис в `compose`.

Выбор — в README.

**Соединение** одно, используется только потоком цикла. Пул не нужен. Автофиксация выключена — транзакции явные.

**Не делает:** не знает про Kafka и оффсеты — если только вы не выберете хранить оффсет рядом с балансом (решение для README, М4, раздел 5).

**Проверка без Kafka** — юнит-тесты: повтор не меняет баланс, два заказа одного продавца суммируются, балансы разных продавцов независимы, данные переживают закрытие и повторное открытие.

#### OffsetTracker

Помнит для каждой назначенной партиции оффсет **следующей** записи после последней обработанной.

**Операции:**

- `done(партиция, оффсет следующей записи)` — запись обработана;
- `snapshot()` — копия текущих оффсетов для коммита, в форме `Map<TopicPartition, OffsetAndMetadata>`;
- `forPartitions(список)` — копия только для указанных партиций, нужна listener'у;
- `remove(список)` — забыть партиции после отзыва или потери.

**Потоки.** Используется только потоком цикла — listener вызывается внутри `poll()` в том же потоке. Синхронизация не нужна. `snapshot()` всё равно отдаёт копию: `commitAsync` может читать переданную карту позже, когда цикл уже изменил трекер.

**Не делает:** не коммитит сам.

#### RebalanceHandler

Реализует `org.apache.kafka.clients.consumer.ConsumerRebalanceListener`, методы — с `@Override`. Получает в конструкторе потребитель и трекер.

| Метод | Действие | Почему |
|---|---|---|
| `onPartitionsRevoked` | `commitSync(tracker.forPartitions(отзываемые))`, затем `tracker.remove(отзываемые)` | последний момент закоммитить, пока партиция ваша (М4, лаба 4.7) |
| `onPartitionsLost` | только `tracker.remove(потерянные)` | партиции уже у других — коммит затрёт их прогресс |
| `onPartitionsAssigned` | вывести в лог | если оффсет хранится в базе — здесь `seek` на оффсет из базы |

Ошибка `commitSync` в `onPartitionsRevoked` — например, `CommitFailedException`, если член уже выбыл, — пишется в лог и не прерывает отзыв. Последствие — повторы у нового владельца, и `BalanceStore` их отсеет.

Время, проведённое в методах listener'а, входит в бюджет `max.poll.interval.ms`.

#### PoisonLog

Файл битых записей. Строка: партиция, оффсет, причина, сырое значение. Сырое значение может содержать что угодно, включая переводы строк, — экранируйте или кодируйте его, например в Base64.

**Почему без очереди и отдельного потока, как журнал в UC-1.** Журнал в UC-1 вызывался из Sender-потока, который нельзя тормозить. Здесь пишет только поток цикла, а битые записи — редкость. Запись прямо в цикле с `flush()` после каждой строки — проще и достаточно.

В модуле 10 эта роль перейдёт к топику мёртвых писем.

### Поток данных

```
                         ProcessingLoop (основной поток)
poll() ──▶ записи ──▶ OrderParser ──битая──▶ PoisonLog ──┐
                          │ OrderEvent                   │
                          ▼                              │
                     BalanceStore.apply ── применён / повтор
                          │                              │
                          ▼                              ▼
                     OffsetTracker.done(партиция, оффсет + 1)
                          │ после пачки
                          ▼
                     commitAsync(tracker.snapshot())

RebalanceHandler (внутри poll(), тот же поток):
    revoked → commitSync(forPartitions(отзываемые)) → remove
    lost    → remove, без коммита
```

### Этап 2.0. Общее хранилище

**Зачем.** Выбор хранилища определяет, будут ли балансы верны при двух экземплярах. Его нужно сделать до кода.

**Что сделать.** H2 с `AUTO_SERVER=TRUE` или PostgreSQL в контейнере. Добавьте драйвер в `pom.xml` модуля. Решите, где файл базы или как поднимается контейнер, и запишите в README.

**Проверка.** Два процесса одновременно подключаются к одной базе — например, две консоли SQL — и видят изменения друг друга.

### Этап 2.1. BalanceStore

**Зачем.** Идемпотентность — свойство хранилища. Если она есть, все сбои Kafka сводятся к «запись пришла ещё раз», и это безопасно. Поэтому хранилище — до потребителя.

**Что сделать.** `BalanceStore` по описанию выше: открытие с созданием таблиц, `apply`, закрытие.

**Проверка.** Юнит-тесты `BalanceStore` — пришлите сигнатуры методов, тесты напишу я.

**Типичные ошибки.** Проверка «уже есть?» отдельным запросом; отметка и баланс в разных транзакциях; идентификаторы обработанных — в памяти процесса.

### Этап 2.2. Цикл poll без коммита

**Зачем.** Убедиться, что потребитель читает, разбирает и применяет записи, прежде чем добавлять коммит и ребалансировку.

**Что сделать.** `ProcessorConfig`, `OrderParser`, `ProcessingLoop` без трекера и коммита, `ProcessorApp` с закрытием в `finally`.

**Проверка.** UC-1 пишет минуту, обработчик читает с начала. Сумма балансов равна сумме заказов в топике. Повторный запуск с той же группой обрабатывает всё снова — коммита нет, — но баланс не меняется: все заказы приходят как повторы.

**Типичные ошибки.** Потребитель создаётся в одном потоке, а `poll()` вызывается в другом; `group.protocol` не задан; `JsonSerde` подключён десериализатором.

### Этап 2.3. Трекер и ручной коммит

**Зачем.** Без коммита каждый перезапуск перечитывает топик с начала. Коммит сокращает повторы до одной пачки.

**Что сделать.** `OffsetTracker`; `done` для каждой записи; `commitAsync` после пачки; `commitSync` в `finally` при штатном выходе.

**Проверка.** Обработать минуту записей, остановить через Ctrl+C, запустить снова без новых записей — ни одного полученного заказа. Закоммиченный оффсет в `kafka-consumer-groups.sh --describe` равен концу каждой партиции.

**Типичные ошибки.** Коммит `offset` вместо `offset + 1`; коммит `consumer.position()` вместо обработанного; трекер отдаёт в `commitAsync` саму карту, а не копию.

### Этап 2.4. Listener

**Зачем.** При ребалансировке партиция уходит к другому экземпляру, и всё, что обработано, но не закоммичено, новый владелец обработает повторно.

**Что сделать.** `RebalanceHandler` по описанию выше; передать в `subscribe`.

**Проверка.** AC2.3; в логе отзыв содержит только переезжающие партиции, а коммит при отзыве — только их оффсеты.

**Типичные ошибки.** Коммит всего трекера в `onPartitionsRevoked`; коммит в `onPartitionsLost`.

### Этап 2.5. Штатная остановка

**Зачем.** Без штатной остановки каждая остановка — как `kill -9`: повторы и ожидание таймаута сессии остальными членами группы.

**Что сделать.** Shutdown hook с `wakeup()` и ожиданием основного потока; `WakeupException` — выход из цикла; финальный коммит и закрытие.

**Проверка.** AC2.6.

**Типичные ошибки.** `WakeupException` пойман общим `catch (Exception)`, и цикл продолжается; shutdown hook не ждёт основной поток.

### Этап 2.6. Битые записи

**Зачем.** Одна запись, которую нельзя разобрать, не должна останавливать обработку навсегда — и не должна исчезнуть без следа.

**Что сделать.** `OrderParser` с результатом из двух вариантов; `PoisonLog`; оффсет битой записи — в трекер.

**Проверка.** AC2.5.

### Этап 2.7. Бюджет poll

**Зачем.** Применение заказа стоит 2 мс в среднем и до 20 мс в пике. Экземпляр не должен выбывать из группы ни при каком из этих значений (М4, раздел 6).

**Что сделать.** Параметр задержки обработки — пауза внутри применения заказа. Расчёт `max.poll.records × 20 мс` против `max.poll.interval.ms` — в README, с выбранными значениями.

**Проверка.** AC2.4.

### Этап 2.8. Групповое применение по продавцу

**Зачем.** Общее решение по числу партиций: при росте нагрузки партиция крупного продавца загружает поток почти на 100%, и дополнительные партиции этого не исправят. Ускорить можно только саму обработку: применять все заказы одного продавца из пачки `poll()` одной транзакцией.

**Что сделать.**

- в `BalanceStore` — операция группового применения: заказы одного продавца, в порядке поступления;
- в одной транзакции: вставить все отметки; заказы, отметка которых нарушила ключ, — повторы; сумма остальных — одним обновлением баланса;
- в `ProcessingLoop` — сгруппировать записи пачки по продавцу. Порядок внутри продавца сохраняется сам: все его заказы в одной партиции, а внутри партиции пачка упорядочена;
- задержка обработки теперь — на транзакцию, а не на заказ: так модель отражает, что дорогое — фиксация транзакции.

**Подумайте:** при нарушении ключа на одном заказе вся транзакция откатится. Как отличить повторы от новых заказов внутри группы, не теряя атомарности? Один из вариантов — сначала узнать, какие из идентификаторов группы уже есть, затем вставить остальные и обновить баланс, всё в одной транзакции. Защитит ли это от одновременной обработки двумя экземплярами при ребалансировке — и если нет, что тогда сработает как последняя линия защиты?

**Проверка.** AC2.7.

### Решения для README

- хранилище и как два экземпляра используют одну базу;
- общий разбор аргументов для двух программ — вынесен или нет и почему;
- `auto.offset.reset` и почему не `latest`;
- что считается битой записью, и почему её оффсет коммитится;
- почему значение разбирается в коде, а не десериализатором;
- почему повтор опознаётся по нарушению ключа, а не проверкой перед вставкой;
- что коммитится в каждом методе listener'а;
- поведение при недоступном хранилище: почему без коммита и без ретраев в цикле;
- хранить ли оффсет ещё и в базе — что это даёт и чего стоит (М4, раздел 5, третий способ);
- расчёт бюджета `poll()`;
- групповое применение: как внутри группы отличаются повторы от новых заказов, и что защищает при одновременной обработке двумя экземплярами.

## UC-3. Переигровка заказов за период

### Цель

Инструмент выгружает все заказы, принятые в заданный интервал времени, из всех партиций топика — например, чтобы перепроверить заказы за время ошибки другого сервиса. Он не входит ни в какую группу и не трогает рабочие группы.

### Архитектура

| Класс | Отвечает за | API Kafka | Почему отдельно |
|---|---|---|---|
| `ReplayApp` | параметры: топик, «с», «по», файл; запуск | — | — |
| `ReplayPlanner` | для каждой партиции вычисляет начало и границу чтения | `partitionsFor`, `offsetsForTimes`, `beginningOffsets`, `endOffsets` | план можно вывести и проверить до чтения |
| `BoundedReader` | читает партиции от начала до границы, фильтрует по времени | `assign`, `seek`, `poll`, `position` | чтение отделено от планирования |
| `ReplayWriter` | пишет записи в файл | — | — |

`ReplayPlanner` и `BoundedReader` могут использовать один `KafkaConsumer` — без `group.id`.

### Поток данных

```
partitionsFor(topic) ──▶ список партиций
offsetsForTimes(«с»)  ──▶ начало по каждой партиции (или null)
endOffsets()          ──▶ граница на момент запуска
beginningOffsets()    ──▶ log start offset — для проверки потери начала
         │ план
         ▼
assign(партиции с началом) → seek(начало) → poll до границы → фильтр по времени → файл
```

### Этап 3.1. План

**Зачем.** Вся логика «откуда и докуда» — в плане. Если план неверен, чтение бесполезно, а проверить план можно без единой выгруженной записи.

**Что сделать.**

- потребитель **без** `group.id` и с `enable.auto.commit=false`: инструмент не участвует ни в каких группах (М4, раздел 11);
- `offsetsForTimes` для каждой партиции со временем «с». Значение `null` означает, что в партиции нет записей не раньше этого времени — партиция пропускается (C1);
- граница — `endOffsets` на момент запуска: всё, что запишут позже, выгружаться не будет (C2);
- потеря начала интервала (C3) — придумайте, как определить по `beginningOffsets`, найденному началу и времени первой записи. Подумайте, почему это можно определить только с оговорками;
- выведите план таблицей: партиция, начало, граница.

**Проверка.** Сравните начало с `kafka-get-offsets.sh --time <мс>` для того же времени — должно совпасть.

**Типичные ошибки.** `group.id` оставлен из `Env` — тогда инструмент — член группы с этим именем; граница вычисляется заново на каждом шаге — при непрерывной записи чтение не закончится.

### Этап 3.2. Ограниченное чтение

**Зачем.** Прочитать ровно план и завершиться.

**Что сделать.**

- `assign` только партиций с найденным началом, `seek` на начало;
- `poll` в цикле; запись берётся, только если её время в интервале;
- партиция считается дочитанной, когда её позиция дошла до границы — а не когда `poll` вернул пусто: пустой ответ значит «пока ничего не пришло», а не «больше ничего нет»;
- дочитанные партиции можно снять с чтения через `pause` или новый `assign` — решите сами;
- инструмент завершается, когда дочитаны все.

Отдельный вопрос — конец интервала. Время записи при `CreateTime` задаёт продюсер, и в партиции оно не обязано расти строго монотонно (М2, раздел 3). Поэтому «остановиться на первой записи позже конца интервала» может пропустить записи. Решите, как обходиться с этим, и запишите.

**Проверка.** AC3.1–AC3.3.

### Критерии приёмки UC-3

| ID | Как воспроизвести | Ожидаемый результат | Доказательство |
|---|---|---|---|
| AC3.1 | три волны записей с паузами по минуте; выгрузить среднюю | в файле ровно записи средней волны | сверка с `kafka-console-consumer.sh --property print.timestamp=true` |
| AC3.2 | одна партиция не получала записей в третьей волне; выгрузить третью | инструмент завершается без ошибки | вывод |
| AC3.3 | UC-1 пишет во время выгрузки | инструмент завершается; в файле нет записей, созданных после запуска | время завершения + сверка |
| AC3.4 | топик с `retention.ms` в 1 минуту, интервал начинается раньше удалённого | выгружено то, что есть, и сообщение о потере начала | вывод |

Для AC3.1 нужен генератор, которому можно задать число заказов. Если в UC-1 его нет, используйте `ProducerProbe` в другой топик того же формата — или добавьте параметр в UC-1.

### Решения для README

- чем `offsetsForTimes` + `seek` лучше `kafka-consumer-groups.sh --reset-offsets` для этой задачи;
- почему пустой `poll()` не означает конец партиции;
- как обрабатывается немонотонное время записей;
- как определяется потеря начала интервала и где это определение ошибается.

## UC-4. Тяжёлая обработка

### Цель

Каждому заказу нужна антифрод-проверка во внешнем сервисе: 50–200 мс, в среднем 100. Проверять нужно 500 заказов в секунду на одном экземпляре. Порядок по продавцу сохраняется. Здесь сходится всё самое сложное в потребителе: пул, обратное давление, коммит только надёжного прогресса (М4, разделы 11 и 12).

### Расчёт до начала

Запишите в README:

- сколько заказов в секунду проверит один экземпляр, если проверять последовательно в потоке `poll()`;
- сколько экземпляров понадобилось бы при модели «потребитель на поток», и хватит ли партиций из этапа 0;
- сколько проверок должно идти одновременно в одном экземпляре, чтобы держать 500 в секунду с запасом.

От этого расчёта зависят размеры пула и очереди.

### Архитектура

| Класс | Отвечает за | API Kafka | Почему отдельно |
|---|---|---|---|
| `FraudApp` | точка входа, остановка | `wakeup()` | — |
| `FraudCheckService` | имитация внешнего вызова: задержка в заданных пределах | — | подменяемая зависимость |
| `OrderedExecutor` | параллельное выполнение с сохранением порядка по продавцу: N однопоточных исполнителей, продавец всегда попадает в один и тот же | — | порядок по ключу при параллельности (М4, раздел 12) |
| `CommitTracker` | для каждой партиции — какие оффсеты в работе, какие готовы, и до какого оффсета всё готово подряд | — | чистая логика, проверяется юнит-тестами |
| `DispatchLoop` | поток `poll()`: раздаёт записи, решает про паузу, коммитит готовый префикс | `poll`, `pause`, `resume`, `paused`, `assignment`, `commitAsync` | **единственный поток, который трогает потребитель** |
| `RebalanceHandler` | что делать с задачами отзываемых партиций | `ConsumerRebalanceListener` | — |

### Главное ограничение дизайна

`KafkaConsumer` не потокобезопасен. Проверки завершаются в потоках пула, но коммит, `pause` и `resume` можно вызывать **только** из потока `poll()`. Поэтому потоки пула лишь отмечают «готово» в потокобезопасной структуре `CommitTracker`, а поток `poll()` на каждом витке читает её и действует. Этот принцип определяет всё остальное.

### Поток данных

```
DispatchLoop (поток poll)                       OrderedExecutor (N потоков)
  poll() ──▶ записи
    │  tracker.started(p, offset)
    └──▶ execute(sellerId, задача) ─────────────▶ FraudCheckService.check(order)
                                                        │
  на каждом витке:                                      │ tracker.completed(p, offset)
    в очереди больше порога? → pause(assignment)  ◀─────┘
    меньше нижнего порога?   → resume(paused)
    commitAsync(tracker.committable())
```

### Этап 4.1. Внешний сервис и упорядоченный пул — без Kafka

**Зачем.** Порядок по ключу при параллельной обработке — отдельная задача. Её проще решить и проверить без потребителя.

**Что сделать.**

- `FraudCheckService.check(order)` — задержка случайной длины в заданных пределах;
- `OrderedExecutor` — N однопоточных исполнителей; номер исполнителя вычисляется из ключа, поэтому задачи одного продавца выполняются в одном потоке по очереди, а разных продавцов — параллельно;
- у каждого исполнителя **ограниченная** очередь; общий счётчик задач в очередях и в работе.

Подумайте о цене этого решения: медленная проверка одного продавца задерживает всех продавцов того же исполнителя.

**Проверка.** Юнит-тест: 10 000 задач по 100 продавцам — для каждого продавца порядок выполнения совпадает с порядком отправки; при N = 50 и задержке 100 мс 10 000 задач выполняются примерно за 20 секунд.

**Типичные ошибки.** Обычный пул на N потоков — порядок по продавцу теряется; неограниченные очереди.

### Этап 4.2. Готовый префикс

**Зачем.** Записи 40, 41, 42 одной партиции проверяются параллельно. Если 42 закончилась первой, коммит 43 объявит 40 и 41 обработанными — при падении они потеряются (М4, раздел 12).

**Что сделать.** `CommitTracker` для каждой партиции:

- `started(offset)` — запись отдана в работу;
- `completed(offset)` — проверка завершена;
- `committable()` — оффсет, до которого **все** записи завершены, плюс один.

Идея вычисления: наименьший оффсет среди ещё не завершённых — это и есть граница. Если незавершённых нет — граница на единицу больше последнего отданного. Структуру данных выберите сами; учтите, что `completed` вызывается из потоков пула, а `committable` — из потока `poll()`.

**Проверка.** Юнит-тесты:

- `started` 40, 41, 42; `completed` 42 → граница 40;
- затем `completed` 40 → граница 41;
- затем `completed` 41 → граница 43;
- ни одной незавершённой → граница = последний отданный + 1.

**Типичные ошибки.** Коммит максимального завершённого оффсета; граница считается без учёта записей, ещё не отданных в работу.

### Этап 4.3. Цикл раздачи без обратного давления

**Зачем.** Собрать поток целиком и увидеть, почему без паузы он ломается.

**Что сделать.** `DispatchLoop`: `poll`, для каждой записи — `started` и отправка в `OrderedExecutor`; на каждом витке — `commitAsync(committable())`. Ограниченная очередь пока может блокировать раздачу — так и оставьте.

**Проверка — намеренная поломка.** Задержка проверки 1 секунда, поток 500 в секунду. Наблюдайте `max.poll.interval.ms`: блокирующая раздача остановит поток `poll()`, и экземпляр выбудет из группы — как в лабе 4.5. Запишите, через сколько секунд это произошло.

### Этап 4.4. Обратное давление

**Зачем.** Когда пул не успевает, поток `poll()` не должен ни блокироваться, ни раздавать без предела (М4, F.A.Q. и раздел 11).

**Что сделать.**

- два порога заполнения: верхний — `pause(assignment())`, нижний — `resume(paused())`. Почему два порога, а не один, — подумайте, что будет на границе с одним;
- раздача больше не блокирует: если на паузе — `poll()` вернёт пусто, и цикл продолжит вызывать его;
- записи, уже полученные в момент паузы, всё равно нужно раздать — решите, что делать, если очередь полна.

**Проверка.** Повторите поломку из этапа 4.3: экземпляр не выбывает, размер очереди не превышает предела, после возврата задержки к 100 мс лаг уменьшается. Это AC4.2.

### Этап 4.5. Ребалансировка

**Зачем.** У отзываемой партиции могут быть задачи в очереди и в работе. Их судьба — отдельное решение.

**Что сделать.** В `onPartitionsRevoked` есть два варианта:

- **дождаться** завершения задач отзываемых партиций, закоммитить готовый префикс и отдать партиции. Ожидание — часть бюджета `max.poll.interval.ms`;
- **бросить** их: убрать из очереди, закоммитить то, что готово сейчас. Брошенные задачи новый владелец выполнит повторно.

Выберите и обоснуйте. В обоих случаях после отзыва задачи этих партиций не должны ничего коммитить. В `onPartitionsLost` — только очистка, без коммита.

**Проверка.** AC4.3 и ребалансировка с добавлением второго экземпляра посреди потока.

### Критерии приёмки UC-4

| ID | Как воспроизвести | Ожидаемый результат | Доказательство |
|---|---|---|---|
| AC4.1 | 5 минут при 500 заказах/с, задержка 50–200 мс | лаг не растёт монотонно | замеры лага раз в 30 с |
| AC4.2 | задержка до 1 с на 2 минуты, затем обратно | очередь не больше предела; ни одного выбывания; лаг после восстановления падает | метрики + лог listener'а |
| AC4.3 | `kill -9` посреди потока, перезапуск | ни одного потерянного заказа; повторных проверок не больше, чем было в очереди и в работе | журнал проверок + сверка |
| AC4.4 | порядок по продавцу | для каждого продавца порядок проверок совпадает с порядком в партиции | журнал проверок + сверка с топиком |

Для AC4.3 и AC4.4 нужен журнал проверок: идентификатор заказа, продавец, партиция, оффсет, время. Пишите его так же, как журнал в UC-1, — не из потоков пула напрямую.

### Решения для README

- размеры пула и очередей — из расчёта;
- почему коммит максимального завершённого оффсета неверен;
- как сохранён порядок по продавцу и какова цена этого решения;
- почему два порога паузы;
- что происходит с задачами отзываемых партиций;
- когда эта модель **не нужна** и «потребитель на поток» лучше.

## UC-5. Наблюдение за отставанием

### Цель

Дежурному нужен инструмент, который по имени группы показывает отставание и поднимает тревогу. Лаг в записях не годится как общий порог: в кластере есть топики и с 500 записями в секунду, и с 5 (М4, раздел 13).

### Архитектура

| Класс | Отвечает за | API Kafka | Почему отдельно |
|---|---|---|---|
| `LagWatchApp` | параметры: группа, период, пороги; цикл замеров | — | — |
| `GroupState` | закоммиченные оффсеты группы и партиции, которые она сейчас читает | `Admin.listConsumerGroupOffsets`, `Admin.describeConsumerGroups` | что знает группа |
| `TopicState` | конец и начало каждой партиции | `Admin.listOffsets` с `OffsetSpec.latest()` и `OffsetSpec.earliest()` | что есть в топике |
| `LagCalculator` | лаг в записях и во времени по каждой партиции | — | чистая логика |
| `AlertRules` | правила T1–T4, хранит историю замеров для T2 | — | чистая логика, юнит-тесты |
| `Reporter` | вывод таблицы и сработавших правил | — | — |

### Правила тревоги

| Правило | Условие |
|---|---|
| T1 — отставание во времени | лаг во времени больше порога по любой партиции |
| T2 — рост | суммарный лаг растёт заданное число замеров подряд |
| T3 — угроза retention | закоммиченный оффсет ближе к log start offset, чем заданная доля размера партиции |
| T4 — нет коммита | у партиции, которую группа читает, нет закоммиченного оффсета |

### Этап 5.1. Состояние группы и топика

**Зачем.** Лаг — разность двух чисел из разных источников: что закоммитила группа и где конец партиции.

**Что сделать.**

- `Admin.create(props)` — без `group.id`: инструмент не входит в группу;
- закоммиченные оффсеты — `listConsumerGroupOffsets(group)`;
- какие партиции группа читает сейчас — назначения членов из `describeConsumerGroups`;
- конец и начало партиций — `listOffsets` с `OffsetSpec.latest()` и `OffsetSpec.earliest()`. `latest()` даёт high watermark, а не LEO (М2, F.A.Q.);
- вывести таблицу: партиция, закоммичено, конец, начало, лаг.

**Проверка.** Лаг по каждой партиции совпадает с `kafka-consumer-groups.sh --describe`.

**Типичные ошибки.** Партиция без коммита получает лаг 0 — та же ловушка, что в лабе 4.10. Партиция без коммита — это отдельное состояние, а не ноль.

### Этап 5.2. Лаг во времени

**Зачем.** Порог во времени одинаково осмыслен для топиков с разным потоком (М4, раздел 13).

**Что сделать.** Два способа — выберите один и обоснуйте:

- **через скорость записи** — по двум последовательным замерам конца партиции: скорость = прирост конца / время между замерами; лаг во времени = лаг / скорость. Не работает, пока в партицию не пишут, и неточен при неровном потоке;
- **через время записи на закоммиченном оффсете** — прочитать одну запись с этого оффсета и взять её время. Точнее, но нужен потребитель: `assign` + `seek` + `poll`, без `group.id`. Это не нарушает требование «не входить в группу».

**Проверка.** На медленном потребителе из лабы 4.10 лаг во времени растёт, и его порядок согласуется с `e2e-макс` зонда.

### Этап 5.3. Правила

**Зачем.** Таблица — для человека, правила — для тревоги.

**Что сделать.** `AlertRules` принимает замер и возвращает сработавшие правила. T2 требует истории замеров — храните последние K сумм. T3 — подумайте, что считать «размером партиции».

**Проверка.** Юнит-тесты на каждое правило: синтетические замеры, при которых правило срабатывает и не срабатывает.

### Критерии приёмки UC-5

| ID | Как воспроизвести | Ожидаемый результат | Доказательство |
|---|---|---|---|
| AC5.1 | медленный потребитель, как в лабе 4.10 | срабатывают T1 и T2; лаг совпадает с `kafka-consumer-groups.sh` по всем партициям | вывод инструмента и утилиты |
| AC5.2 | все потребители группы остановлены | лаг продолжает расти в выводе | вывод |
| AC5.3 | новая группа с `latest` и медленный потребитель, как в исходной лабе 4.10 | T4 по партициям без коммита | вывод |
| AC5.4 | топик с `retention.ms` в 2 минуты, остановленная группа | T3 срабатывает раньше, чем retention обгонит группу | вывод + `kafka-get-offsets.sh --time -2` |

### Решения для README

- способ подсчёта лага во времени, где он ошибается и почему этого достаточно;
- что считается «размером партиции» в T3;
- какие ситуации инструмент не ловит — например, прыжок `latest` из лабы 4.4 — и как их можно было бы обнаружить.
