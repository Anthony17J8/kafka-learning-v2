**Когда:** после модуля 4, перед модулем 5
**Время:** 8–10 часов
**Предварительно:** теория и практика модулей 3 и 4
**Результат:** Maven-модуль с вашим кодом, README к каждому use case с обоснованием решений, `notes/clients-own-code.md` с результатами приёмки

## Правила блока

Практикумы модулей 3 и 4 построены на готовых зондах — это измерительные приборы. Здесь вы пишете продюсер и консьюмер сами.

1. **Код пишется с нуля.** Во время работы не открывайте `ProducerProbe`, `ConsumerProbe`, `ManualCommitConsumer`, `ProducerModes`, `TenantPartitioner`. Источники — теория модулей 3 и 4, Javadoc `KafkaProducer` и `KafkaConsumer`, документация конфигурации на kafka.apache.org.
2. **Зонды и утилиты Kafka можно использовать для проверки** — как генератор нагрузки или измеритель, — но не как образец кода.
3. **Требования описывают поведение, а не реализацию.** Как устроить классы, где хранить состояние, каким способом считать — решаете вы. Каждое неочевидное решение записывается в README use case в разделе «Решения» с ответом на вопрос «почему так, а не иначе».
4. **Use case закрыт, когда все критерии приёмки пройдены и у каждого есть доказательство** — команда и её вывод в `notes/clients-own-code.md`. «Работает» без вывода не считается.
5. **Окружение** — одиночный брокер из `compose.single.yml`. Кластер нужен только там, где это сказано явно.

### Где писать код

Создайте в `labs/` новый Maven-модуль — например, `own-clients` — и подключите его в `labs/pom.xml`. Зависимость от `common` можно использовать: `Env`, `OrderEvent` и сериализация JSON оттуда — общая инфраструктура, а не решение задачи.

## Общий контекст

Маркетплейс. Покупатели оформляют заказы, каждый заказ — событие `OrderEvent` из `common`: идентификатор заказа, продавец, сумма, тенант, время создания. События идут в топик `orders.created.v1`.

Нагрузка:

- обычная — 500 заказов в секунду, пиковая — 2000;
- продавцов — около 1000, заказы распределены между ними неравномерно;
- обработчиков заказов в пике будет до 8 экземпляров.

Требование бизнеса к порядку: **события одного продавца обрабатываются в том порядке, в котором были приняты.** От этого зависит баланс продавца, который пересчитывается по каждому заказу.

### Решения, общие для всех use case

Запишите их в `README.md` модуля до начала UC-1:

- **ключ записи** — что используется ключом и почему, исходя из требования к порядку (М2, раздел 2);
- **число партиций** `orders.created.v1` — расчёт от нагрузки и числа обработчиков, с учётом делимости (М2, раздел 9; М4, раздел 2 и F.A.Q.);
- **`min.insync.replicas` и `acks`** — что выбрано для учебного одиночного брокера и что было бы в продакшене с RF=3 (М3, раздел 5).

## UC-1. Приём заказов

### Контекст

Сервис приёма получает заказы от витрины и публикует их в `orders.created.v1`. Витрину имитирует встроенный генератор с настраиваемой скоростью.

Для бизнеса недопустимо одно: **заказ, который сервис принял, не может исчезнуть молча.** Он должен либо оказаться в топике, либо быть явно зафиксирован как неотправленный — с причиной, — чтобы его можно было переотправить.

### Основной сценарий

1. Генератор создаёт заказы с заданной скоростью.
2. Сервис принимает заказ и отправляет его в Kafka, не блокируя приём следующих.
3. По подтверждению брокера заказ считается доставленным.
4. При штатной остановке сервис прекращает приём, дожидается судьбы всех принятых заказов и завершается.

### Альтернативные сценарии

| # | Ситуация | Требуемое поведение |
|---|---|---|
| A1 | брокер временно недоступен, меньше `delivery.timeout.ms` | заказы доставляются после восстановления; потерь нет |
| A2 | брокер недоступен дольше `delivery.timeout.ms` | каждый недоставленный заказ зафиксирован как неотправленный, с причиной; по нему можно установить, ушёл ли он в топик на самом деле |
| A3 | буфер продюсера заполнен | сервис не зависает бесконечно: время ожидания ограничено, превышение — явный отказ в приёме, который виден в метриках сервиса |
| A4 | заказ не проходит проверку размера | отказ без повторов, заказ зафиксирован с причиной |
| A5 | в конфигурации задано противоречие гарантиям — например, `acks=1` | сервис отказывается стартовать, а не работает с ослабленными гарантиями |
| A6 | штатная остановка во время потока | ни один принятый заказ не остаётся без судьбы |

### Требования

**Функциональные:**

- R1.1 — для каждого принятого заказа можно установить его итоговую судьбу: подтверждён или не отправлен с причиной;
- R1.2 — ошибки доставки разделяются на ретраибельные и окончательные; повторы делает клиент, а не ваш код;
- R1.3 — `ProducerInterceptor` собственной реализации считает отправленные, подтверждённые и неудачные записи и раз в N секунд выводит счётчики;
- R1.4 — скорость генератора задаётся параметром запуска.

**Нефункциональные:**

- R1.5 — сервис выдерживает 2000 заказов в секунду на одиночном брокере без ошибок;
- R1.6 — ни callback, ни интерсептор не выполняют медленной работы в Sender-потоке;
- R1.7 — все настройки продюсера, влияющие на гарантии, заданы явно.

### Ограничения

- одна копия `KafkaProducer` на сервис;
- никаких `send().get()` в основном потоке приёма.

### Критерии приёмки

| ID | Как воспроизвести | Ожидаемый результат | Доказательство |
|---|---|---|---|
| AC1.1 | 5 минут при 500 заказах/с, затем 1 минута при 2000/с | ноль ошибок; число заказов в топике равно числу принятых | счётчики интерсептора, `kafka-get-offsets.sh` |
| AC1.2 | `docker pause kafka` на 10 с во время потока | ноль неотправленных; все принятые — в топике | судьба каждого заказа + сверка с топиком |
| AC1.3 | пауза брокера дольше `delivery.timeout.ms` (как в лабе 3.8) | каждый недоставленный заказ зафиксирован; число зафиксированных равно `record-error-total`; вы можете показать, какие из них всё-таки оказались в топике | сверка множеств по идентификаторам заказов |
| AC1.4 | маленький `buffer.memory` и пауза брокера (как в лабе 3.7) | время блокировки приёма не превышает выбранного порога; отказы видны в метриках сервиса | строки метрик сервиса |
| AC1.5 | запуск с `acks=1` | сервис не стартует, понятная ошибка | вывод запуска |
| AC1.6 | SIGTERM во время потока при 500 заказах/с | у каждого принятого заказа есть итоговая судьба | сверка множеств |

### Решения, которые нужно обосновать в README

- как сервис хранит судьбу заказа и почему этот способ не замедляет Sender-поток;
- какое значение `max.block.ms` и почему; что видит витрина при отказе в приёме;
- какое значение `delivery.timeout.ms` и от чего оно зависит в продакшене;
- `linger.ms` и `batch.size` для нагрузки 500–2000 заказов в секунду — с опорой на замеры модуля 3;
- что делать с неотправленными заказами: кто и как их переотправит, и почему переотправка может дать дубль (М3, лаба 3.8).

## UC-2. Обработка заказов

### Контекст

Обработчик читает `orders.created.v1` и по каждому заказу пересчитывает баланс продавца: прибавляет сумму заказа. Результат хранится в локальном хранилище — выбор за вами: встраиваемая база (H2, SQLite) или файл.

Повторная обработка заказа удвоит сумму на балансе продавца. **Баланс должен быть верным при любых сбоях и ребалансировках.**

### Основной сценарий

1. Экземпляр вступает в группу и получает партиции.
2. Для каждого заказа пересчитывает баланс продавца.
3. Регулярно фиксирует прогресс в Kafka.
4. При штатной остановке фиксирует прогресс и выходит из группы.

### Альтернативные сценарии

| # | Ситуация | Требуемое поведение |
|---|---|---|
| B1 | экземпляр убит `kill -9` посреди потока | после перезапуска балансы верны; заказы, обработанные до сбоя, не учтены дважды |
| B2 | в группу добавлен экземпляр или один экземпляр остановлен | балансы верны, повторов на балансе нет |
| B3 | экземпляр выбыл из группы по таймауту `poll()` | он не портит прогресс нового владельца партиций |
| B4 | в топике встретилась запись, которую нельзя разобрать как `OrderEvent` | обработка не останавливается навсегда; запись зафиксирована с партицией и оффсетом |
| B5 | штатная остановка | после перезапуска не обработана повторно ни одна запись |

### Требования

**Функциональные:**

- R2.1 — ручной коммит; гарантия доставки — at-least-once;
- R2.2 — результат обработки effectively-once: повторно полученный заказ не меняет баланс (М4, раздел 5);
- R2.3 — собственный `ConsumerRebalanceListener`, поведение которого в каждом методе соответствует М4, раздел 9;
- R2.4 — штатная остановка через `wakeup()` из другого потока;
- R2.5 — сервис считает и выводит: обработано, пропущено как повтор, битых записей.

**Нефункциональные:**

- R2.6 — `group.protocol=consumer`;
- R2.7 — обработка одного заказа — 2 мс в среднем, до 20 мс в пике; сервис ни при каком из этих значений не выбывает из группы по таймауту `poll()`. Бюджет посчитан и записан в README (М4, раздел 6).

### Критерии приёмки

| ID | Как воспроизвести | Ожидаемый результат | Доказательство |
|---|---|---|---|
| AC2.1 | UC-1 пишет 100 000 заказов; два экземпляра обработчика | сумма балансов равна сумме всех заказов; каждый заказ учтён один раз | запрос к хранилищу + сверка с топиком |
| AC2.2 | три раза `kill -9` одного экземпляра посреди потока, каждый раз с перезапуском | то же; число пропущенных как повтор больше нуля | счётчики сервиса + сверка |
| AC2.3 | во время потока добавить третий экземпляр, затем штатно остановить один (как в лабе 4.7) | то же | счётчики + сверка |
| AC2.4 | искусственно замедлить обработку до 20 мс на заказ на 2 минуты | ни одного выбывания из группы | лог событий listener'а |
| AC2.5 | записать в топик консольным продюсером строку, не являющуюся JSON | обработка продолжается; битая запись зафиксирована | вывод сервиса |
| AC2.6 | штатная остановка, затем перезапуск без новых записей | ни одной повторно полученной записи | счётчики сервиса |

### Решения, которые нужно обосновать в README

- как устроена идемпотентность: что хранится, в какой транзакции с балансом, и почему повтор не изменит баланс;
- что коммитится в `onPartitionsRevoked` и почему в `onPartitionsLost` ничего не коммитится;
- где хранится оффсет — только в Kafka или ещё и в хранилище рядом с балансом, — и что это меняет при назначении партиции (М4, раздел 5, третий способ);
- что делается с битой записью и почему её нельзя просто пропустить без следа.

## UC-3. Переигровка заказов за период

### Контекст

Вчера с 14:00 до 14:30 у одного из сервисов-потребителей была ошибка, и заказы за этот период нужно выгрузить для повторной проверки. Нужен инструмент, который выгружает все заказы, принятые в заданный интервал времени, во всех партициях топика.

### Основной сценарий

1. Инструмент получает топик и интервал «с — по».
2. Для каждой партиции находит начало интервала.
3. Читает записи до конца интервала и выгружает их в файл.
4. Завершается сам, когда все партиции прочитаны до конца интервала.

### Альтернативные сценарии

| # | Ситуация | Требуемое поведение |
|---|---|---|
| C1 | в партиции нет записей позже начала интервала | партиция корректно пропускается, без ошибки |
| C2 | в партицию продолжают писать во время выгрузки | инструмент не читает бесконечно: граница чтения фиксируется в момент запуска |
| C3 | начало интервала раньше log start offset | инструмент выгружает то, что есть, и явно сообщает, что начало интервала уже удалено retention |

### Требования

- R3.1 — инструмент не состоит ни в какой группе и ничего не коммитит; рабочие группы при этом не затрагиваются (М4, раздел 11);
- R3.2 — поиск начала интервала — через запрос оффсета по времени, без перебора записей;
- R3.3 — выгружаются все записи интервала по времени записи (`timestamp`), и только они.

### Критерии приёмки

| ID | Как воспроизвести | Ожидаемый результат | Доказательство |
|---|---|---|---|
| AC3.1 | три волны записей с паузами по минуте; выгрузить среднюю | в файле ровно записи средней волны | сверка с `kafka-console-consumer.sh --property print.timestamp=true` |
| AC3.2 | одна из партиций не получает записей в третьей волне; выгрузить третью | инструмент завершается без ошибки | вывод инструмента |
| AC3.3 | UC-1 пишет во время выгрузки | инструмент завершается; в файле нет записей, созданных после запуска | время завершения + сверка |
| AC3.4 | топик с `retention.ms` в 1 минуту, интервал начинается раньше удалённого | выгружено то, что есть; сообщение о потере начала интервала | вывод инструмента |

### Решения, которые нужно обосновать в README

- чем этот способ лучше `kafka-consumer-groups.sh --reset-offsets` для такой задачи;
- как определяется, что партиция прочитана до конца интервала, и почему недостаточно дождаться пустого `poll()`.

## UC-4. Тяжёлая обработка

### Контекст

Для части заказов нужна антифрод-проверка во внешнем сервисе. Вызов занимает 50–200 мс, в среднем 100. Внешний сервис выдерживает параллельные запросы. Нужно проверять 500 заказов в секунду.

Порядок по продавцу из общего контекста сохраняется: проверки одного продавца выполняются в порядке поступления заказов.

### Задача на расчёт перед началом

Запишите в README до написания кода:

- сколько заказов в секунду проверит один экземпляр, если обрабатывать последовательно в потоке `poll()`;
- сколько экземпляров понадобилось бы при модели «потребитель на поток», и хватит ли для этого партиций из общего решения;
- какой уровень параллелизма нужен в одном экземпляре, чтобы проверять 500 заказов в секунду с запасом.

### Основной сценарий

1. Поток `poll()` получает заказы и передаёт их на проверку в пул.
2. Пул выполняет проверки параллельно, соблюдая порядок по продавцу.
3. Прогресс фиксируется только по полностью проверенным заказам.

### Альтернативные сценарии

| # | Ситуация | Требуемое поведение |
|---|---|---|
| D1 | внешний сервис замедлился до 1 с на вызов на 2 минуты | память не растёт без предела; экземпляр не выбывает из группы; после восстановления отставание рассасывается |
| D2 | экземпляр убит `kill -9` | после перезапуска ни один заказ не потерян; повторно проверены только заказы, бывшие в работе |
| D3 | ребалансировка во время работы пула | проверки отозванных партиций не фиксируются после отзыва; прогресс нового владельца не испорчен |

### Требования

- R4.1 — ограниченная очередь между потоком `poll()` и пулом; при её заполнении — `pause`, при освобождении — `resume` (М4, разделы 11 и 12);
- R4.2 — коммитится только непрерывный обработанный префикс каждой партиции (М4, раздел 12);
- R4.3 — проверки одного продавца не выполняются параллельно и не переставляются;
- R4.4 — вызов внешнего сервиса имитируется задержкой со случайным временем в заданных пределах; пределы — параметр запуска.

### Критерии приёмки

| ID | Как воспроизвести | Ожидаемый результат | Доказательство |
|---|---|---|---|
| AC4.1 | 5 минут при 500 заказах/с, задержка 50–200 мс, один экземпляр | лаг не растёт монотонно | замеры лага раз в 30 с |
| AC4.2 | задержка до 1 с на 2 минуты, потом обратно | число задач в очереди не превышает её размера; ни одного выбывания из группы; лаг после восстановления падает | метрики сервиса + лог listener'а |
| AC4.3 | `kill -9` посреди потока, перезапуск | ни один заказ не потерян; число повторных проверок не больше размера очереди плюс число задач в работе | сверка множеств |
| AC4.4 | проверить порядок по продавцу | для каждого продавца порядок проверок совпадает с порядком в партиции | журнал проверок + сверка с топиком |

### Решения, которые нужно обосновать в README

- как выбран размер пула и очереди — из расчёта перед началом;

## UC-5. Наблюдение за отставанием

### Контекст

Дежурному нужен инструмент, который по имени группы показывает, насколько она отстаёт, и поднимает тревогу, когда отставание опасно. Лаг в записях не подходит: в кластере есть и топик заказов на 500 записей в секунду, и топик отчётов на 5 (М4, раздел 13).

### Основной сценарий

1. Инструмент раз в N секунд снимает состояние группы через Admin API.
2. Для каждой партиции считает лаг в записях и во времени.
3. Выводит таблицу и отдельной строкой — сработавшие правила тревоги.

### Правила тревоги

| Правило | Условие |
|---|---|
| T1 — отставание во времени | лаг во времени больше заданного порога по любой партиции |
| T2 — рост | суммарный лаг растёт на протяжении заданного числа замеров подряд |
| T3 — угроза retention | закоммиченный оффсет партиции ближе к log start offset, чем заданная доля размера партиции |
| T4 — нет коммита | у партиции, которую группа читает, нет закоммиченного оффсета |

### Требования

- R5.1 — только Admin API; инструмент не вступает в группу;
- R5.2 — партиция без коммита не считается партицией с нулевым лагом (М4, раздел 13);
- R5.3 — способ подсчёта лага во времени — на ваш выбор, с обоснованием: через скорость записи между замерами или через время записи на закоммиченном оффсете;
- R5.4 — пороги правил — параметры запуска.

### Критерии приёмки

| ID | Как воспроизвести | Ожидаемый результат | Доказательство |
|---|---|---|---|
| AC5.1 | медленный потребитель, как в лабе 4.10 | срабатывают T1 и T2; лаг в записях совпадает с `kafka-consumer-groups.sh` по всем партициям | вывод инструмента + вывод утилиты |
| AC5.2 | все потребители группы остановлены | инструмент продолжает показывать растущий лаг | вывод инструмента |
| AC5.3 | новая группа с `auto.offset.reset=latest`, медленный потребитель, как в исходной лабе 4.10 | T4 срабатывает для партиций без коммита | вывод инструмента |
| AC5.4 | топик с `retention.ms` в 2 минуты и остановленная группа | T3 срабатывает до того, как retention обгонит группу | вывод инструмента + `kafka-get-offsets.sh --time -2` |

### Решения, которые нужно обосновать в README

- какой способ подсчёта лага во времени выбран, где он ошибается и почему этого достаточно;
- какие ещё ситуации инструмент не ловит — например, прыжок `latest` из лабы 4.4 — и как их можно было бы обнаружить.
